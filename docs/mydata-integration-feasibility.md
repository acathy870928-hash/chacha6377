# 마이데이터(본인신용정보관리) 연동 가능성 검토

- 작성일: 2026-08-26
- 대상: `chacha6377` 서비스의 금융 마이데이터 연동
- 상태: 초안 (사업 요건 확정 전 사전 검토)

> ⚠️ 본 문서의 법·제도 수치(자본금, 심사기간, 토큰 유효기간, 과금 등)는 **최종 확인 대상**입니다.
> 실제 추진 시 금융위원회 고시·`마이데이터 지원포털`·금융보안원 기술 가이드라인의 **최신본**을 반드시 재확인해야 합니다.

---

## 0. 결론 요약

**기술적으로는 가능합니다. 다만 "기술 난이도"가 아니라 "인허가 요건"이 실질적인 관문입니다.**

마이데이터 연동은 아무나 API 키를 발급받아 붙일 수 있는 오픈 API가 아니라,
**금융위원회 허가를 받은 본인신용정보관리회사(마이데이터 사업자)만** 정보제공자(은행/카드/증권 등)의
표준 API를 호출할 수 있는 구조입니다.

따라서 가능 여부는 다음 셋 중 어느 경로를 택하느냐로 갈립니다.

| 경로 | 가능성 | 소요 기간(추정) | 초기 비용(추정) | 비고 |
|---|---|---|---|---|
| **A. 직접 허가 취득 후 연동** | 가능하나 高난도 | 12~18개월 | 수억 원대 | 자본금·인력·보안설비 요건 충족 필요 |
| **B. 기존 마이데이터 사업자와 제휴** | 현실적 (권장) | 2~4개월 | 낮음(제휴 수수료) | 데이터 재제공 범위에 법적 제약 있음 |
| **C. 마이데이터가 아닌 대체 수단** | 가능 (기능 제한) | 1~2개월 | 낮음 | 오픈뱅킹/공공마이데이터/제휴 API |
| **D. 스크래핑 / 대리 로그인** | **불가 (위법 소지)** | - | - | 2022년부터 API 방식 의무화, 채택 금지 |

**권고:** 우선 **C(대체 수단)로 MVP를 검증**하고, 데이터 범위가 정말 마이데이터급이어야 한다면
**B(제휴)로 상용화**, 마이데이터 자체가 핵심 사업 모델일 때만 **A(직접 허가)**를 추진합니다.

## 1. 검토 전제 및 확인 필요 사항

현재 저장소(`chacha6377`)에는 코드가 없어 **기존 시스템 기반의 기술 검토는 수행하지 못했습니다.**
아래 항목이 확정되어야 경로 선택과 상세 설계가 가능합니다.

| # | 확인 항목 | 왜 필요한가 |
|---|---|---|
| 1 | 당사가 마이데이터 허가를 보유했는가 / 취득 의사가 있는가 | 경로 A vs B 결정 |
| 2 | 당사가 정보제공자(금융회사)인가, 정보이용자인가 | 의무 사항이 정반대 |
| 3 | 실제로 필요한 데이터 범위 (계좌잔액? 거래내역? 카드승인? 보험? 투자?) | 오픈뱅킹만으로 충분할 수 있음 |
| 4 | B2C 앱인가, B2B 솔루션인가 | 전송요구·동의 UX 설계가 달라짐 |
| 5 | 개인 식별정보 저장 여부 및 보관 기간 정책 | 파기 의무·보안 설계 범위 |

## 2. 제도 요건 (경로 A: 직접 허가)

### 2.1 근거
- 「신용정보의 이용 및 보호에 관한 법률」상 **본인신용정보관리업(허가제)**
- 감독: 금융위원회 허가 / 금융감독원 심사

### 2.2 주요 허가 요건 (확인 필요 — 최신 고시 기준 재확인)

| 요건 | 내용 |
|---|---|
| 자본금 | 최소 5억 원 이상 |
| 물적 설비 | 전산설비, 보안설비, 정보보호 시스템, 사무공간 |
| 인적 요건 | 임원 결격사유 없음, 신용정보관리·보호인 선임, 전문인력 확보 |
| 대주주 요건 | 재무건전성, 사회적 신용 (제재 이력 등) |
| 사업계획 | 타당성·건전성 심사 |

### 2.3 예상 소요
- 서류 준비 3~6개월 → 심사 3~6개월 → 기능적합성/보안점검 2~3개월
- **실무 기준 총 12~18개월**을 잡는 것이 안전합니다.

### 2.4 허가 이후 지속 의무
- 신용정보관리·보호인 상시 운영 및 정기 점검
- 겸영·부수업무 신고
- 정보보호 조치 및 감독당국 정기 보고
- 정보전송요구 **주기적 갱신(재동의)** 관리

## 3. 기술 아키텍처 (연동 시 실제로 만들어야 하는 것)

### 3.1 방식
- **표준 API 방식만 허용.** 스크래핑·ID/PW 대리 저장 방식은 금지되었습니다.
- 정보제공자는 표준 규격에 따라 API를 제공할 의무가 있고, 이용자는 규격대로 호출합니다.

### 3.2 핵심 구성요소

```
[사용자]
   │ ① 전송요구 + 통합인증(간편인증/전자서명)
   ▼
[당사 마이데이터 서비스] ──② OAuth 2.0 인가코드/토큰──▶ [정보제공자 or 중계기관]
   │                                                          │
   │ ◀────────────── ③ 표준 API 응답(계좌/카드/보험/투자 등) ──┘
   ▼
[수집·저장·분석] → 파기 정책 적용
```

| 구성요소 | 역할 |
|---|---|
| 마이데이터 지원포털 / 종합포털 | 사업자 등록, 통계, 전송내역 관리 |
| 중계기관 | 소규모 정보제공자 API를 대신 중계 |
| 통합인증기관 | 사용자 본인확인 및 전송요구 인증 |
| 금융보안원 | 기능적합성 심사, 보안취약점 점검 |

### 3.3 인증/인가
- **OAuth 2.0 Authorization Code Grant** 기반
- Access Token / Refresh Token 발급 및 갱신 로직 필요
  (유효기간 정책은 규격 최신본 확인 필요 — 통상 access는 단기, refresh는 전송요구 기간에 연동)
- **전송요구서**: 정보주체가 어떤 기관의 어떤 정보를, 어느 기간 동안 전송할지 명시 → 만료 시 **재동의 필요**
- 채널 보안: 상호 TLS(mTLS), 전문 암호화, 인증서 관리

### 3.4 반드시 통과해야 하는 관문
1. **기능적합성 심사** — 표준 API 규격을 정확히 구현했는지 검증
2. **보안취약점 점검** — 애플리케이션/인프라 취약점 진단
3. 위 2개를 통과해야 **서비스 오픈 가능** (개발 완료 ≠ 오픈 가능)

### 3.5 인프라 고려사항
- 클라우드 이용 가능하나 **금융권 클라우드 이용 절차(안전성 평가·보고)** 선행 필요
- 접근통제, 로그 보존, 암호화 키 관리, 망분리 관련 규제 준수
  (망분리 규제는 완화 논의가 진행되어 왔으므로 **현행 기준 재확인 필요**)
- 개인신용정보 **가명처리/파기** 프로세스 자동화 필요

## 4. 경로별 상세 검토

### A. 직접 허가 취득
- **장점**: 데이터 접근 범위 최대, 서비스 자유도 높음, 진입장벽 자체가 해자
- **단점**: 기간·비용·상시 컴플라이언스 부담이 큼
- **적합**: 마이데이터가 핵심 수익모델일 때만

### B. 기존 마이데이터 사업자와 제휴 ✅ 현실적 권장안
- 허가 보유 사업자의 서비스를 **화이트라벨/제휴 형태**로 활용
- **⚠️ 핵심 제약**: 마이데이터 사업자가 수집한 개인신용정보를 **제3자에게 재제공하는 것은 별도 동의와 법적 제약**을 받습니다.
  "우리가 데이터를 받아서 우리 DB에 쌓는다"는 형태는 대부분 **불가**할 수 있습니다.
  → 계약 전 반드시 법무·컴플라이언스 검토 필요
- **적합**: 조회·분석 결과만 필요하고 원본 데이터 축적이 필수가 아닐 때

### C. 마이데이터 외 대체 수단
| 수단 | 얻을 수 있는 것 | 진입 난이도 |
|---|---|---|
| 오픈뱅킹 (금융결제원) | 계좌 조회, 잔액, 거래내역, 출금/입금 이체 | 중 (이용기관 등록 필요) |
| 공공 마이데이터 (행안부) | 주민등록/소득/자격 등 공공 증명 정보 | 중 |
| 카드사·증권사 제휴 API | 개별 기관 한정 데이터 | 기관별 협의 |
| PDF/파일 업로드 파싱 | 사용자가 직접 제출한 내역 | 낮음 |
- **다수 서비스가 실제로 필요한 것은 "계좌 잔액 + 거래내역"이며, 이는 오픈뱅킹으로 충분한 경우가 많습니다.**

### D. 스크래핑 / 대리 로그인 ❌
- 2022년 표준 API 전면 시행과 함께 사실상 금지
- 정보통신망법·신용정보법 위반 소지 및 금융회사 약관 위반
- **채택 금지**

## 5. 개발 관점 체크리스트 (경로 A/B 공통)

- [ ] 전송요구 동의 UX (기관 선택 → 항목 선택 → 기간 → 통합인증)
- [ ] OAuth 토큰 저장소 (암호화, 기관별 다중 토큰, 자동 갱신)
- [ ] 전송요구 만료 D-30 알림 및 재동의 플로우
- [ ] 정기 전송 스케줄러 (호출 주기 제한 준수, 백오프/재시도)
- [ ] 표준 응답 스키마 매핑 계층 (기관별 예외 처리)
- [ ] 개인신용정보 암호화 저장 + 파기 배치
- [ ] 전 API 호출 감사 로그 (누가/언제/무엇을)
- [ ] 기능적합성 심사용 테스트 케이스 세트
- [ ] 보안취약점 점검 대응 (SAST/DAST 사전 수행)
- [ ] 장애 시 폴백 및 사용자 안내

### 예상 일정 (경로 B 기준)

| Phase | 기간 | 산출물 |
|---|---|---|
| 요건 확정 · 제휴사 선정 | 2~3주 | 데이터 범위 정의서, 제휴 LOI |
| 법무/컴플라이언스 검토 | 2~4주 | 재제공 가능 범위 확인서 |
| 연동 설계·개발 | 6~8주 | 동의 플로우, 수집 파이프라인 |
| 보안 점검·오픈 준비 | 2~4주 | 취약점 조치 완료 보고 |

## 7. 다음 단계 (의사결정 요청)

1. **데이터 범위를 확정해 주세요.** 계좌 잔액·거래내역 수준이면 오픈뱅킹으로 대체 가능하며, 마이데이터 추진이 불필요할 수 있습니다.
2. **마이데이터 허가 취득 의사를 확정해 주세요.** (A vs B 분기점)
3. **법무 검토를 착수해 주세요.** 특히 경로 B의 "데이터 재제공 가능 범위"는 기술 설계 이전에 답이 나와야 합니다.

### 확인처
- 금융위원회 / 금융감독원 (허가 요건·심사 절차)
- 마이데이터 지원포털 (사업자 등록, 기술 규격, 참여기관 현황)
- 금융보안원 (기술 가이드라인, 기능적합성 심사, 보안취약점 점검)
- 금융결제원 (오픈뱅킹 이용기관 등록)
