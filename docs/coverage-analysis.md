# 보장분석 연동

마이데이터(한국신용정보원)로 조회한 **보장분석 리포트**를 시스템에 붙이면,
지금 설계에서 가장 크게 비어 있던 두 곳이 메워진다.

## 리포트에 들어 있는 것

| 항목 | 예 | 우리 쪽 용도 |
| --- | --- | --- |
| 보험사 · 상품명 | `KB다이렉트플러스운전자보험(무배당)(24.10)` | **상품 특정** — 되묻기 불필요 |
| 계약년월 | `2024.11` | **약관 판 특정** — 되묻기 불필요 |
| 가입담보명 · 가입금액 | `골절진단비(치아파절포함)(연간1회한) 10만원` | **가입 여부 확정** |
| 만기 · 납입 · 보험료 | `2044.11`, `월납/20년`, `14,800원` | 참고 |
| 한장보장현황(권장/가입/부족) | 41개 표준 보장항목 | 보장 갭 안내 |

상품명 끝에 판 표기가 그대로 실려 오는 경우도 있다(`(24.10)`, `(2001)`).
계약년월과 함께 쓰면 판 특정이 한층 확실해진다.

## 해결되는 문제 1 — 되묻기

기존 흐름은 보상 질문마다 **보험사 → 상품 → 가입 시점**을 되물어야 했다.
리포트가 있으면 셋 다 이미 정해져 있다.

```
[기존]  음주운전 사고인데 나오나요?
        → 어느 보험사? → 어느 상품? → 언제 가입? → 답변       (되묻기 3회)

[보장분석] 음주운전 사고인데 나오나요?
        → 답변                                              (되묻기 0회)
```

`plan_turn(..., coverage=profile)`에 리포트를 넘기면 특정 단계를 건너뛴다.
리포트에 없는 상품을 물으면 기존 되묻기 경로로 자연스럽게 되돌아간다.

## 해결되는 문제 2 — 「약관에 있다」와 「가입했다」의 차이

약관에는 그 상품에서 가입할 수 있는 담보가 전부 들어 있어서,
약관만으로는 「이 계약이 그 담보에 가입했는가」를 알 수 없었다
(`docs/routing.md` 참조). 그래서 답변이 언제나 조건부였다.

리포트에는 실제 가입 담보와 금액이 있으므로 확정해서 답할 수 있다.

- **가입한 경우** — 어느 계약에 얼마인지까지 제시
- **가입하지 않은 경우** — `NextAction.NOT_ENROLLED`로 약관을 뒤지지 않고 바로 답한다

## 새로 생기는 능력 — 청구 누락 방지

같은 담보가 여러 계약에 흩어져 있는 일이 흔하다.

```
골절진단비(치아파절포함)(연간1회한)   KB손보  운전자보험     10만원
5대골절진단비                       KB손보  운전자보험     20만원
골절진단비(치아제외)                 DB손보  브라보라이프    30만원
```

한 건만 청구하고 나머지를 놓치기 쉬운 지점이다.
`CoverageProfile.find_benefits()`는 **전 계약에 걸쳐** 찾고, 답변은 걸린 것을 모두 보여준다.
이름을 포함하는 변형 담보(`5대골절진단비`)도 함께 건다.
좁혀서 놓치는 것보다 넓게 걸어 FA가 판단하게 하는 편이 낫다.

**괄호 안 표기는 절대 잘라 쓰지 않는다.**
`골절진단비(치아파절포함)`과 `골절진단비(치아제외)`는 지급 범위가 다르다.
비교할 때만 정규화하고 화면에는 원문을 그대로 보여준다.

## 한계 — 확정 근거는 아니다

리포트가 스스로 밝히는 제약이며, 답변에도 반영해야 한다.

- **조회 범위** — 손해보험 2002년 12월, 생명보험 2000년 4월, 공제 2009년 10월 이후
  계약만 조회된다. 그 이전 계약은 리포트에 아예 없다.
- **단독실손** — 기간 안에 가입했더라도 납입주기 · 납입기간 · 보험료 등이 제공되지 않는다.
- **지급 근거가 될 수 없다** — 「정확한 내용은 가입한 회사의 약관 및 보험증권을 확인」해야 한다.
- **약관을 봐야 아는 것들** — 가입 1년 이내 50% 감액, 동일 사고 중복지급 제한 등.
- **조회 시점 기준** — 이후 신규 가입 · 해지는 반영되지 않는다. 답변에 기준일을 밝힌다.

그래서 「가입 담보가 없다」는 답변도 단정하지 않는다.

> 보장분석 기준으로 「치아보철치료」 담보에 가입한 계약이 없습니다.
> 조회되지 않는 계약(오래된 계약 · 단독실손 등)이 있을 수 있으니 증권으로 한 번 더 확인해 주세요.

## 보장분석과 약관은 역할이 다르다

둘을 합쳐야 보상 질문에 온전히 답한다.

| | 답하는 것 |
| --- | --- |
| **보장분석** | 이 계약이 **무엇에 얼마** 가입했는가 |
| **약관(VELUGA)** | 그 담보가 **어떤 경우에 지급되고 언제 면책인가** |

「골절진단비 10만원 가입」만으로는 이번 사고에 지급되는지 알 수 없고,
약관만으로는 이 사람이 가입했는지 알 수 없다.
보장분석이 **어느 약관의 어느 판을 볼지**까지 정해 주므로 두 소스가 자연스럽게 이어진다.

## 개인정보

리포트는 계약 · 보험료 · 피보험자 정보를 담은 개인정보다.
저장소에는 실제 리포트 데이터를 넣지 않는다.
테스트 픽스처(`tests/test_coverage.py`)는 구조만 본뜬 가상 데이터다.

## 남은 작업

- **담보명 매핑** — 리포트 담보명, 한장보장현황의 41개 표준 항목, 약관 조항의 담보명이
  서로 다르게 표기된다. 세 층을 잇는 매핑이 실제 구현의 핵심 작업이 된다.
- **리포트 파싱** — 현재는 데이터 모델만 있다. 실제 연동 형식(API 응답 / PDF / DB)이
  정해지면 로더를 붙인다.
- **피보험자 구분** — 계약자와 피보험자가 다른 계약이 있다(부모가 계약자인 경우).
  누구의 사고인지에 따라 대상 계약이 달라진다.
