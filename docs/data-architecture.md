# AI 데이터 구조 (AX팀 공유 기준)

챗봇이 답변에 사용하는 데이터의 전체 구조. AX팀 공유 내용을 기준으로 정리하며,
자료 업로드 방법(유효기간 설정 · 태그 체계)은 추후 공유 예정이므로 TBD로 둔다.

## 이번 작업 범위

대상은 **신규 서비스**다(제품명 미정, 코드명 `orca`는 작업용일 뿐이다).
기존 Orca AI(iFA Ai Link)의 확장이 아니며, 시장 분석(`docs/market.md`) 위에서 새로 만든다.
기존 Orca AI · 모홈 화면은 UI · 데이터 구조의 참고 레퍼런스로만 쓴다.

이번에 연결하는 소스는 **Micky DATA · VELUGA DATA 2종뿐이다.** 둘 다 검색형이므로
이번 범위에서는 API형(My DATA / Cloud DATA) 경로를 구현하지 않는다.

| 소스 | 이번 범위 | 비고 |
| --- | --- | --- |
| Micky DATA | ✅ 연결 | 보험 전문지식 |
| VELUGA DATA | ✅ 연결 | 보험약관 자료 |
| External MCP | ⏸ 이후 | 통로 추가 방식이라 소스가 계속 늘어남 |
| BumE_C / BumE_F | ⏸ 이후 | |
| My DATA / Cloud DATA | ⏸ 이후 | API형. 경로 자체가 다름 |

아래 전체 구조는 이후 확장 시 기준으로 남겨둔다.

### 주 사용 시나리오: 보상 질문

VELUGA(약관) 데이터를 붙이는 주된 이유는 **보상 관련 질문**이다.
「이런 경우에 보험금이 나오나요」, 「면책 사유에 해당하나요」 같은 질문이 중심이 된다.

**1차 오픈 대상은 FA다.** 고객이 직접 쓰는 화면이 아니라 FA가 상담·응대 과정에서 쓰는 도구다.
(2차에서 고객용으로 넓힐 때 재검토할 항목은 `docs/plan.md` 0절에 정리했다.)
이 전제에서 아래가 따라온다.

- **되묻기가 실제로 동작한다.** FA는 상품·특약·가입 시점을 알고 있으므로,
  상품이나 약관 판이 특정되지 않으면 되물어서 좁히는 방식이 실용적이다.
- **조항 원문을 그대로 보여주는 것이 유용하다.** FA는 약관 용어를 읽을 수 있고,
  고객에게 근거를 제시해야 하므로 요약보다 원문 인용이 필요한 경우가 많다.
- **모바일 화면 제약** — 조항 원문은 길다. 요약을 먼저 보이고 원문은 펼쳐보는 형태가 맞다.
- **톤은 실무형** — 「지급됩니다 / 안 됩니다」로 단정하는 대신
  해당 조항과 확인이 필요한 쟁점을 짚어주고, 최종 판단은 보상 심사로 넘긴다.
  FA가 그대로 고객에게 옮길 수 있는 수준의 정확도가 기준이다.

이 시나리오는 일반적인 문서 검색과 성격이 다르며, 아래 네 가지가 정확도를 좌우한다.

**1. 특약 단위 구분이 핵심이다.**
약관 한 건에 주계약과 수십 개 특약이 함께 들어 있다. 청크에 소속(주계약 / 특약명)을
메타데이터로 달지 않으면 **다른 특약의 조항을 근거로 답하는 오답**이 나온다.
보상 질문에서 가장 흔한 실패 원인이므로 청킹 단계에서 반드시 처리한다.

**2. 조항 유형 태깅이 필요하다.**
보상 질문은 약관에 쓰인 표현과 다른 말로 들어온다.
예) 질문 「음주운전 사고인데 보험금 나오나요」 → 약관 「피보험자가 음주운전을 하는 동안…」
의미 검색만으로는 약하므로, 조항을 유형별로 태깅해 함께 검색한다.

- 지급사유 (보험금을 지급하는 경우)
- 면책 (보험금을 지급하지 않는 사유)
- 감액지급
- 대기기간 / 면책기간
- 지급제한 조건 (가입 전 발병, 고지의무 위반 등)

질문이 「나오나요」 한 줄이어도 **지급사유와 면책을 항상 함께** 제시해야 한다.
지급사유만 보여주면 면책에 걸리는 건을 「나온다」고 오해하게 만든다.

**3. 약관 판(version)이 결정적이다.**
보상은 **계약 체결 시점의 약관**이 적용된다. 최신 약관으로 답하면 틀린 답이 된다.
따라서 모든 청크에 상품명 · 판/개정 차수 · 시행일을 메타데이터로 붙이고,
검색 시 해당 판으로 한정해야 한다.

⚠️ 다만 「이 고객이 언제 어느 상품에 가입했는가」는 계약 정보(Cloud DATA / My DATA)이며
**이번 범위 밖**이다. 따라서 이번 단계에서는 상품·시점을 사용자가 지정하거나,
특정되지 않으면 되묻는 방식으로 처리한다. 임의로 최신 판을 골라 답하지 않는다.

**4. 단정하지 않는다.**
약관 조항 확인은 지급 여부의 확정이 아니다. 실제 지급은 사실관계 확인과 심사를 거친다.
답변은 근거 조항을 인용해 제시하되, 최종 판단은 보상 심사임을 함께 안내한다.

### VELUGA 연동 방식

VELUGA는 **업체(벤더)가 이미 RAG로 구축해 둔 벡터DB를 검색해서 쓴다.**
즉 약관 원문 수집 · 파싱 · 청킹 · 임베딩 · 색인은 벤더 쪽에 있고,
우리는 **검색 결과를 받아 답변을 구성하는 쪽**을 담당한다.

따라서 앞서 정리한 요건(특약 구분, 조항 유형 태깅, 판 관리)은
우리가 구현할 항목이 아니라 **벤더 인덱스가 이미 갖추고 있는지 확인할 항목**이 된다.
벤더 청킹이 특약을 구분하지 않으면 우리 답변 정확도의 상한이 거기서 정해지므로,
착수 전에 확인이 필요하다.

**연동 형태 (확인됨)**

- 인터페이스는 **API**.
- **LLM 모델을 우리가 선택**할 수 있고, 그 모델로 **생성된 답변까지** 반환한다.

즉 검색뿐 아니라 생성까지 벤더 API 안에서 끝난다. 우리 쪽 역할은 그만큼 줄어들지만,
그 대신 **답변 품질을 프롬프트로 제어할 수 있는지**가 핵심 쟁점이 된다.
보상 답변의 요건(지급사유와 면책을 함께 제시, 단정 회피, 조항 인용)은
생성 단계에서 결정되는데, 그 생성이 벤더 쪽에 있기 때문이다.

**벤더 측에 추가로 확인할 것**

1. 생성된 답변과 함께 **근거 청크(출처 조항)도 반환되는가**
   → 반환되지 않으면 FA에게 근거 조항을 제시할 수 없다. 보상 용도에서는 사실상 필수.
2. **프롬프트 제어 가능 여부** — 시스템 프롬프트나 답변 형식을 우리가 지정할 수 있는가
   - 가능 → 보상 답변 요건을 우리가 주입한다
   - 불가 → 벤더 기본 톤을 그대로 쓰게 되므로, 사전에 답변 품질 검수가 필요하다
3. 선택 가능한 **모델 목록**과 모델별 비용 · 응답 지연
4. 검색만 하고 생성은 건너뛰는 모드가 있는가 (retrieval-only)
   → 있으면 Micky 결과와 합쳐 우리가 직접 생성하는 선택지가 열린다
5. 멀티턴 지원 여부 — 되묻기 후 이어지는 대화를 API가 이어받는가,
   아니면 매 호출이 단발인가 (되묻기 설계가 여기서 갈린다)
6. 청크 메타데이터에 무엇이 실려 있는가
   - 상품명 / 보험사
   - 주계약 · 특약 구분 (**가장 중요**)
   - 조 · 항 · 호 위치
   - 약관 판 · 시행일
   - 조항 유형(지급사유 / 면책 등) 태그 유무
7. 검색 시 메타데이터 필터가 되는가 (상품·판 한정 검색 가능 여부)
8. 커버리지 — 어느 보험사 · 어느 상품 · 어느 시점까지 색인돼 있는가
9. 갱신 주기 — 약관 개정분이 언제 반영되는가
10. 인증 방식 · 호출 한도 · 응답 지연

**우리 쪽 담당 범위 (확정 전 잠정)**

생성까지 벤더가 하므로, 우리 범위는 아래로 좁혀진다.

- 질문 라우팅 (Micky / VELUGA / 둘 다)
- **되묻기** — 상품·약관 판이 특정되지 않은 질문을 벤더 API에 넘기기 전에 좁힌다
  (벤더가 한 번에 답을 생성해 버리므로, 되묻기는 앞단에서 처리해야 한다)
- 사용할 LLM 모델 선택 및 프롬프트 주입(가능한 경우)
- 답변 표시 — 요약 + 근거 조항 펼쳐보기, 출처 표기
- Micky 결과와 VELUGA 결과를 함께 써야 하는 질문의 결합 처리
- 근거가 없을 때 추측하지 않고 모른다고 답하기

## 대원칙

AI는 가지고 있는 자료만큼만 답한다. 따라서 데이터 소스의 종류와 **시점(언제 기준 자료인가)**이
답변 품질을 결정한다. 지난 기준으로 답하는 것은 답하지 않는 것보다 위험하다.

## 두 갈래 구분

데이터는 처리 방식에 따라 두 가지로 갈리며, **응답 방식이 서로 다르다.**

| 구분 | 비유 | 성격 | 응답 방식 |
| --- | --- | --- | --- |
| **찾아 읽는 자료** (검색형) | 도서관에서 책을 찾아 읽고 설명 | 글로 정리된 자료. 상대적으로 정적 | AI가 관련 부분을 찾아 **이해해서 설명** |
| **시스템에서 불러오는 정보** (API형) | 서랍을 열어 서류를 꺼내옴 | 사람마다 다르고 매일 바뀌는 값 | 실제 값을 **그대로 표시** |

이 구분이 중요한 이유: 「내 수수료가 얼마인가」 같은 질문은 API로 가져온 실제 값만 보여주며,
AI가 임의로 생성해 답하는 일이 없어야 한다.

- 검색형 소스: Micky DATA / VELUGA DATA / External MCP / BumE_C / BumE_F
- API형 소스: My DATA / Cloud DATA

## 설계에 반영해야 할 점

### 이번 범위 (Micky + VELUGA)

1. **출처 표기** — 어느 소스의 어느 문서를 근거로 했는지 함께 제시한다.
   특히 약관(VELUGA DATA)은 조항(조·항·호) 단위 근거가 필요하다.
2. **소스 구분 유지** — 두 소스는 성격이 다르다.
   Micky는 개념·이론 설명(예: 「글라이드패스가 뭔가요?」),
   VELUGA는 특정 상품의 약관 조항 확인(예: 「오토파일럿 변액연금…」).
   한 답변에 섞일 때 어느 문장이 약관 근거인지 구분되어야 한다.
3. **시점 관리** — 자료를 넣는 일보다 시기별로 관리하는 일이 더 큰 과제.
   유효기간이 지난 자료가 검색 결과에 섞이지 않도록 인덱스 단계에서 걸러야 한다.
   약관은 상품 개정 이력이 있으므로 **판(version)·시행일** 관리가 특히 중요하다.
4. **모르면 모른다고 답하기** — 검색 결과에 근거가 없으면 추측해 답하지 않는다.

### 이후 확장 시

5. **응답 경로 분리** — 질문을 검색형/API형으로 라우팅하고, API형 답변에는 AI 생성 텍스트가
   값 자체를 대체하지 않도록 한다.
6. **대상(권한) 기반 필터링** — 소스마다 대상이 다르다(고객 / FA / 관리자 / 스태프).
   같은 질문이라도 사용자 역할에 따라 접근 가능한 소스가 달라진다.
   (Micky·VELUGA는 둘 다 FA·고객 공통, 외부공개 가능이라 이번 범위에선 분기가 없다.)
7. **소스 레지스트리** — External MCP는 통로가 계속 늘어나므로 소스를 하드코딩하지 않는다.
