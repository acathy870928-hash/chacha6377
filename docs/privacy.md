# 보장분석 데이터와 개인정보

보장분석은 고객이 **본인인증으로 전송요구권을 행사해** 조회한 마이데이터다.
그런데 약관 검색은 외부 벤더 API에서 이뤄지고, 1차 사용자는 FA다.
「고객 개인정보를 FA가 쓰는 AI에, 그리고 외부 벤더에 보내도 되는가」가 문제가 된다.

결론부터. **설계로 대부분 끊을 수 있다.** 남는 것은 동의 범위 확인이며 법무 판단이 필요하다.

## 1. 벤더에는 개인정보를 보내지 않는다

벤더가 약관을 찾는 데 필요한 것은 **누구의 계약인지가 아니라 어느 약관인지**다.

| 보내는 것 | 보내지 않는 것 |
| --- | --- |
| 보험사 · 상품명 | 이름 · 생년월일 · 연락처 |
| 약관 판 (계약년월에서 우리가 계산) | 계약번호 · 증권번호 |
| 담보명 | **가입금액 · 보험료** |
| 상황 서술 (정제된 문장) | 계약자 · 피보험자 |

가입금액도 보낼 필요가 없다. 약관은 「지급사유에 해당하는가」만 답하고,
금액은 **우리 쪽에서 답변을 조립할 때** 붙인다.

```
보장분석(개인정보)  ──  우리 서버에만 머문다
        │
        │  상품 · 판 · 담보명만 추출          ← vendor_query.build_queries()
        ▼
   TermsQuery  ──────  벤더 API (누구 것인지 모른다)
        │
        │  조항 원문 반환
        ▼
   답변 조립     ──────  우리 서버에서 가입금액 · 계약과 결합
```

이 분리가 코드로 강제된다. `TermsQuery`에 필드를 추가하면 테스트가 깨지도록
잠금장치를 걸어 두었다(`tests/test_vendor_query.py`).

### 질문 원문이 구멍이다

FA가 「김○○ 고객이 계단에서…」처럼 입력하면 분리가 깨진다.
그래서 **질문 원문을 그대로 벤더에 보내지 않는다.**
분류기가 정리한 상황 서술만 싣고, 실명 호칭 · 주민번호 · 연락처는
`strip_pii()`로 한 번 더 걸러낸다. (완전한 비식별화가 아니라 마지막 방어선이다.)

## 2. 자체 RAG(Micky)도 같은 원칙

Micky는 우리 시스템이지만 생성에 LLM을 쓴다.
외부 LLM API를 쓴다면 **처리위탁 · 국외이전** 검토 대상이 되므로,
보장분석 데이터를 프롬프트에 넣을 때 같은 기준을 적용한다.

## 3. 접근 통제 — FA가 아무 고객이나 보면 안 된다

1차가 FA용이므로 **FA ↔ 고객 관계 확인**이 전제다.

- 담당 고객이 아닌 사람의 보장분석은 불러올 수 없어야 한다.
- 세션에 올린 고객 컨텍스트는 상담이 끝나면 내린다.
- **누가 · 언제 · 누구의 데이터를 조회했는지 로그를 남긴다.**
  마이데이터 기반 정보는 조회 이력 관리가 특히 중요하다.
- 화면에 고객이 특정되어 있음을 항상 표시한다(컨텍스트 바).
  다른 고객 데이터로 답하고 있는 것을 아무도 모르는 상태가 가장 위험하다.

## 4. 확인이 필요한 것 — 법무 판단 영역

아래는 설계로 해결되지 않으며, 동의서와 계약서를 봐야 한다.
(여기 적힌 것은 확인 항목이지 법률 판단이 아니다.)

1. **동의 범위** — 고객이 보장분석에 동의할 때 받은 이용 목적에
   「AI 상담 지원」이 포함되는가. 리포트 발행까지만 동의했다면 목적이 추가된 것이다.
2. **보관 기간** — 리포트 조회 시점 기준 데이터를 얼마나 들고 있을 것인가.
   조회일(`CoverageProfile.as_of`)을 답변에 표시하는 것과 별개로 보관 정책이 필요하다.
3. **제3자 제공 / 처리위탁** — 벤더에 나가는 값이 개인정보가 아니라는 판단을
   법무에서 확인받는다. 위 1번 표가 그 근거 자료가 된다.
4. **마이데이터 사업자 계약** — 보장분석 발행 업체와의 계약에
   데이터 2차 활용(AI 상담) 범위가 어떻게 되어 있는가.
5. **고객 열람 · 삭제 요구** — 고객이 삭제를 요구하면 세션 · 로그에서
   어떻게 지울 것인가.

## 5. 최소 안전 설계 — 동의가 확인되기 전에도 가능한 방식

동의 범위가 확인되지 않았다면, 보장분석을 **저장하지 않고 세션에서만 쓰는** 방식이 있다.

- FA가 상담 중 보장분석을 조회하면 그 세션에서만 컨텍스트로 사용
- 서버에 영속 저장하지 않음 (로그에도 담보명 · 상품명 수준까지만)
- 세션 종료 시 폐기

기능은 그대로 동작하고, 보관에 따르는 쟁점은 줄어든다.
다만 「등록할 약관 목록 도출」(`aggregate_terms_needs`)에는 집계가 필요하므로,
그 용도로는 **개인을 식별하지 않는 형태**(보험사 + 상품 + 계약년월 + 건수)로만 쌓는다.
이 집계값은 개인정보가 아니다.

## 요약

| 쟁점 | 해결 |
| --- | --- |
| 벤더에 개인정보가 나가는가 | 나가지 않는다. 질의를 상품 · 판 · 담보로 제한 (코드로 강제) |
| 질문 원문에 실명이 섞이면 | 정제된 상황 서술만 전송, PII 패턴 필터 |
| FA가 남의 고객을 보면 | 담당 관계 확인 + 조회 로그 + 화면에 대상 고객 표시 |
| 보관이 부담되면 | 세션 한정 사용, 집계는 비식별 형태로만 |
| 동의 범위 | **법무 확인 필요** — 설계로 해결되지 않음 |
