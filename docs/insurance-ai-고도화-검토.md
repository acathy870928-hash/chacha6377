# Insurance AI 고도화 아이디어 검토 의견

> 대상: 「가입설계서 기반 보험사고(Event) 보장 시나리오 서비스」 고도화 기획안
> 작성 목적: 제시된 4단계 고도화 방향에 대한 타당성 검토 및 실행 시 선결 과제 정리

---

## 1. 검토 결론

**최종 방향(4단계)에 동의합니다.** 특히 2단계에서 3단계로 전환한 판단 — 고객 중심 데이터 구성을
포기하고 보험사고(Event) 중심으로 축을 바꾼 것 — 은 이 기획안에서 가장 가치 있는 의사결정입니다.
개인정보·민감정보 축적이라는 최대 리스크를 제거하면서도 활용성의 상당 부분을 보존했습니다.

다만 아래 세 가지는 기획안에서 과소평가되어 있으며, 이 중 하나라도 해결되지 않으면 서비스가
동작하지 않거나 컴플라이언스 사고로 이어질 수 있습니다.

| 과제 | 현재 기획안에서의 취급 | 실제 난이도 |
| --- | --- | --- |
| 담보 명칭 표준화 (Coverage Taxonomy) | 언급 없음 | **최대 병목**. 이것이 서비스 품질을 결정 |
| 가입설계서에 잔존하는 개인정보 | 3단계에서 해소된 것으로 전제 | 미해소. 설계서에 피보험자 식별정보 포함 |
| 생성 결과물의 보험안내자료 해당 여부 | 언급 없음 | 법무·준법감시 사전 검토 필수 |

또한 차별화 논리를 **아이디어의 신규성**이 아니라 **데이터 자산과 워크플로우 진입점**으로
재정의할 것을 제안합니다 (5장).

---

## 2. 단계별 전개에 대한 평가

### 2-1. 1단계 → 2단계 (보상금액 시뮬레이션)를 접은 판단

"유사 서비스가 이미 존재한다"는 이유로 접었으나, **더 중요한 이유가 하나 더 있습니다.**

보상금액을 합산하여 제시하는 기능은 부당 안내 리스크가 매우 높습니다. 실제 지급은 약관상
지급조건, 면책기간, 감액기간, 1회한 규정, 동일 재해 한도, 수술 분류표 해당 여부 등에 따라
달라지며, AI가 산출한 금액과 실제 지급액이 다를 경우 그 책임은 안내한 설계사와 회사로
귀속됩니다.

따라서 **금액 합산 시뮬레이션을 버린 것은 차별화 이슈가 아니라 리스크 관리 측면에서도 옳은
결정**이며, 4단계 설계에서도 "총 얼마를 받는다"는 형태의 합산 금액 제시는 도입하지 않을 것을
권고합니다. 담보별 개별 조건 제시로 한정해야 합니다.

### 2-2. 2단계 → 3단계 전환 (고객 중심 → Event 중심)

핵심적으로 옳은 전환입니다. 고객별 가입보험 정보를 축적하는 순간 다음이 모두 적용됩니다.

- 개인정보보호법상 **민감정보**(건강·질병 정보) — 별도 동의 필요
- 개인정보보호법상 **고유식별정보** 처리 근거
- 신용정보법상 **개인신용정보** (보험계약 정보) — 수집·이용·제공 각각의 근거 필요
- 사고·질병 이력이 붙는 순간 사실상 건강정보 DB가 되어 보관·파기·접근통제 요구수준 급상승

Event 중심 구조는 이 전부를 회피합니다. **Event → 담보 → 지급조건 매핑 데이터에는 개인정보가
전혀 포함되지 않으므로, 데이터 자산 자체를 개인정보 규제 밖에서 축적할 수 있습니다.** 이는
장기적으로 매우 큰 이점입니다.

### 2-3. 4단계에서 부수적으로 얻는 이점 (기획안에 명시되지 않음)

4단계는 **신규 가입설계서**를 대상으로 하므로, 필요한 약관은 **현재 판매 중인 상품의 현행
약관**뿐입니다. 1단계에서 언급했던 "가입시점에 맞는 약관을 불러오는" 문제 — 즉 과거 약관
아카이브 구축과 계약시점-약관 버전 매칭 — 이 **범위에서 사라집니다.**

이는 구축 난이도를 크게 낮추는 요인이므로 기획안에 명시적으로 기재할 가치가 있습니다.
반대로 향후 "기존 계약 보장분석"으로 확장할 경우 이 문제가 다시 발생하므로, 로드맵상
별도 단계로 분리해 두어야 합니다.

## 3. 반드시 선결해야 할 과제

### A. 담보 표준코드 체계 (Coverage Taxonomy) — 최대 병목

기획안은 "Event → 관련 가능 담보"를 연결한다고 기술하고 있으나, **어떤 담보에 연결할
것인지**가 정의되어 있지 않습니다. 실무상 담보 명칭은 다음과 같이 흩어져 있습니다.

- 보험사마다 명칭이 다름 (예: 골절진단비 / 골절진단비Ⅱ / 골절(치아파절제외)진단비)
- 동일 보험사도 상품·개정마다 명칭과 담보코드가 다름
- 동일 명칭이라도 약관상 대상 KCD 코드 범위가 다름

Event를 상품별 실제 담보명에 직접 매핑하면 매핑 건수가
`Event 수 × 보험사 수 × 상품 수 × 개정 횟수`로 폭증하여 유지보수가 불가능합니다.

**제안 구조 — 2단 매핑**

```
Event  ──(1:N)──▶  표준담보코드  ──(N:M)──▶  상품별 실제 담보
                   (자체 정의)              (Micky DATA 기반 정규화)
```

- Event 데이터는 **표준담보코드에만** 매핑 → Event 사전의 규모가 `Event 수 × 표준담보 수`로 고정
- 상품별 담보를 표준담보코드로 정규화하는 작업은 Micky DATA 적재 단계에서 1회 수행
- 신규 상품 출시 시에도 정규화 매핑만 추가하면 Event 사전은 수정 불필요

**이 정규화의 정확도가 곧 서비스 품질입니다.** 설계서상 담보를 표준코드로 잘못 매핑하면
시나리오에서 담보가 누락되거나 없는 보장이 있다고 안내됩니다. 착수 시 가장 먼저 자원을
투입해야 할 영역이며, 자동 매핑 + 사람 검수(HITL)를 전제로 설계해야 합니다.

**KCD 코드를 매개로 활용할 것을 권고합니다.** 약관의 지급조건은 대부분 별표 분류표(KCD 코드
목록)로 규정되어 있으므로, `Event → KCD 코드군 → 표준담보`로 연결하면 매핑 근거가 명확해지고
검증이 가능해집니다.

### B. 가입설계서에 잔존하는 개인정보 — 3단계 우려는 아직 해소되지 않음

기획안은 3단계 전환으로 개인정보 이슈가 해결된 것으로 서술하고 있으나, **4단계의 입력물인
가입설계서에는 피보험자 식별정보가 포함**됩니다.

- 피보험자 성명, 생년월일, 성별, 직업(급수)
- 태아보험의 경우 모(母) 정보 및 출산예정일
- 계약자 정보, 설계사 코드

즉 **Event 데이터에는 개인정보가 없지만, 처리 과정에는 개인정보가 유입**됩니다.

**제안 — 무저장(Stateless) 처리 원칙**

1. 업로드 즉시 필요 항목만 추출: `담보명 / 가입금액 / 납입기간 / 보험기간 / 연령 / 성별`
2. 성명·생년월일·연락처·증권번호 등 식별정보는 추출 단계에서 폐기 (연령·성별은 요율 및
   담보 가입가능 여부 판단에 필요하므로 유지)
3. 원본 파일은 처리 완료 후 즉시 삭제, 세션 종료 시 추출 데이터도 폐기
4. 로그·프롬프트 기록에 원본이 남지 않도록 마스킹 정책 적용 (LLM 호출 로그 포함)

이 원칙을 지키면 3단계에서 우려했던 사항이 실제로 해소되며, 이 설계 자체를 기획안에 명시해야
법무 검토가 통과 가능한 형태가 됩니다. 반대로 "설계서를 저장해두고 나중에 다시 본다"는 편의
기능을 추가하는 순간 3단계에서 회피한 문제가 그대로 돌아옵니다.

### C. 생성 결과물의 법적 성격 — 보험안내자료 해당 여부

이 서비스의 산출물은 **설계사가 고객에게 보험을 설명하는 데 사용**됩니다. 따라서 산출물이
보험업법상 보험안내자료 또는 금융소비자보호법상 설명자료·광고에 해당하는지에 대한 판단이
선행되어야 합니다. 해당된다면 준법감시인 사전 심의 대상이 될 수 있습니다.

**여기서 구조적 문제가 발생합니다.** LLM이 매번 자유 서술형으로 생성하는 문장은 사전 심의가
불가능합니다. 심의를 통과한 문구만 사용하려면 생성 방식 자체를 제약해야 합니다.

**제안 — 템플릿 고정 + 슬롯 채우기 방식**

- 시나리오 카드의 문장 구조를 사전에 확정하고 심의를 받음
- LLM은 자유 문장을 생성하지 않고, 정해진 슬롯(담보명, 가입금액, 지급조건 요약)만 채움
- 지급조건 요약도 약관 원문 인용 또는 사전 승인된 표현으로 제한
- 단정적 표현 금지: "보상받을 수 있습니다" → "○○담보에서 보장 여부를 확인할 수 있습니다"
- 모든 카드에 고정 문구 부기: 실제 지급 여부는 약관 및 보험금 심사 결과에 따름

이 제약은 서비스 품질을 떨어뜨리는 것이 아니라, **오히려 출력 일관성을 높이고 환각을 구조적으로
차단**하는 효과가 있습니다. 자유 서술형 생성은 이 도메인에서 채택하지 않을 것을 권고합니다.

### D. 면책·감액·대기기간 — 차별화의 실제 지점

기획안의 골절 예시(`진단 → 깁스 → 수술 → 입원 → 후유장해`)는 방향은 옳으나, 실제로 설계사가
곤란해지는 지점은 "무엇이 보장되는가"가 아니라 **"무엇이 보장되지 않는가"**입니다.

- 깁스는 수술이 아니므로 수술비 담보 미해당 (별도 깁스치료비 담보 가입 시에만 보장)
- 치아 파절은 골절진단비 대상에서 제외되는 경우가 많음
- 암 관련 담보의 90일 면책 및 1년 이내 50% 감액
- 동일 담보 1회한 규정, 동일 재해 한도
- 수술 분류표 미해당 처치

**"이건 안 됩니다"를 함께 제시하는 것이 경쟁 서비스 대비 실질적 차별점이자, C항의 컴플라이언스
방어 수단이기도 합니다.** 두 목적이 상충하지 않고 같은 방향을 가리킵니다.

따라서 시나리오 카드에 **「주의 안내」 섹션을 필수 구성요소로 포함**할 것을 권고합니다. 보장
담보만 나열하는 카드는 생성하지 않도록 강제하는 것이 좋습니다.

### E. 가입설계서 파싱 — 한 줄로 처리되어 있으나 실제 체감 품질의 절반

기획안은 "가입담보 및 가입금액 분석"을 한 단계로 기술하고 있으나, 실무상 설계서 PDF는
보험사·채널·설계 시스템마다 레이아웃이 상이하고, 표 구조 추출 실패가 빈번합니다. 담보 하나를
놓치면 시나리오 전체가 잘못됩니다.

**우선 검토할 대안:** 파일 업로드가 아니라 **비교추천 시스템 또는 설계 시스템과 연동하여
구조화된 설계 데이터를 직접 수신**할 수 있는지 확인하는 것입니다. 가능하다면 파싱 문제가
사라지고 정확도가 근본적으로 달라집니다. 연동이 불가능한 경우에만 PDF 파싱으로 진행하되,
**추출된 담보 목록을 설계사가 확인·수정하는 단계를 UI에 반드시 포함**해야 합니다.

## 4. 데이터 구조 제안

### 4-1. Claim Event 정의

```yaml
event_id: EV_HFMD_001
event_name: 수족구병
category: 영유아 감염질환
kcd_codes: [B08.4, B08.5]          # 약관 별표와의 연결 고리
typical_age_band: [0, 7]
sub_events:                         # 하나의 사고에서 파생되는 후속 상황
  - 외래 진료
  - 입원
  - 합병증 진단
related_coverages:                  # 표준담보코드로만 매핑
  - code: STD_DIAG_INFECT
    relation: 조건부                 # 확정 / 조건부 / 참고
    condition_note: 약관상 대상 감염병 분류표 해당 여부 확인 필요
  - code: STD_HOSP_DAILY
    relation: 조건부
    condition_note: 입원 시에만 해당, 면책일수 확인 필요
caution_points:                     # 주의 안내 (필수)
  - 외래 진료만 발생한 경우 입원 관련 담보는 해당하지 않습니다
  - 대상 감염병 분류표 포함 여부는 상품별로 다를 수 있습니다
```

`relation` 필드를 두는 이유는, AI가 "보장됩니다"와 "확인이 필요합니다"를 구분해서 출력하도록
데이터 레벨에서 강제하기 위함입니다.

### 4-2. Event 흐름(Sequence) 정의

골절처럼 하나의 사고가 여러 단계로 전개되는 경우, 단계를 명시적으로 데이터화합니다.

```yaml
event_id: EV_FRACTURE_001
event_name: 골절
sequence:
  - step: 진단          related_coverages: [STD_DIAG_FRACTURE]
  - step: 깁스치료      related_coverages: [STD_CAST_TREAT]
    caution: 깁스는 수술에 해당하지 않으므로 수술 관련 담보와 구분됩니다
  - step: 수술          related_coverages: [STD_SURG_GENERAL, STD_SURG_ACCIDENT]
    caution: 약관상 수술 분류표 해당 여부에 따라 달라집니다
  - step: 입원          related_coverages: [STD_HOSP_DAILY, STD_HOSP_ACCIDENT]
  - step: 후유장해      related_coverages: [STD_DISABILITY_ACCIDENT]
    caution: 지급률에 따라 보험금이 달라집니다
```

### 4-3. 처리 흐름 (기획안 보완)

```
가입설계서 입력
  → [파싱] 담보명·가입금액 추출 + 식별정보 폐기
  → [정규화] 상품별 담보명 → 표준담보코드           ★ 신설
  → [검증] 설계사 확인·수정 UI                      ★ 신설
  → [매칭] Event 데이터에서 관련 표준담보 탐색
  → [조회] 해당 상품 약관에서 실제 지급조건 확인
  → [보완] Micky DATA로 일반지식 보완
  → [생성] 고정 템플릿에 슬롯 채우기                ★ 자유생성 아님
  → 시나리오 카드 (보장 + 주의 안내)
```

## 5. 차별화 논리의 재정의

기획안은 1단계를 "유사 서비스 존재"를 이유로 접었습니다. 그러나 **4단계 역시 아이디어 자체로는
모방 가능**하며, 경쟁사가 동일한 컨셉을 발표하는 데 큰 장벽은 없습니다.

실제 진입장벽은 아이디어가 아니라 다음 세 가지입니다.

1. **데이터 자산** — 표준담보 taxonomy와 Event-담보 매핑은 도메인 지식이 축적된 결과물이며,
   축적량 자체가 해자가 됩니다. 후발주자가 단기간에 복제하기 어렵습니다.
2. **Micky DATA의 상품·담보 커버리지** — 이미 보유한 자산이며, 경쟁사가 동일 수준의 커버리지를
   확보하는 데 시간이 소요됩니다.
3. **워크플로우 진입점** — 설계서는 설계사가 이미 만드는 산출물입니다. 사용자가 사고를 직접
   입력해야 하는 서비스는 사용되지 않지만, 이미 존재하는 산출물을 입력으로 받는 서비스는
   사용됩니다. 기획안 후반부의 "AI가 대표 시나리오를 먼저 제시" 방식은 이 관점에서 매우
   중요하며, 부가 옵션이 아니라 **기본 동작으로 확정**할 것을 권고합니다.

따라서 기획안의 차별화 서술을 "새로운 아이디어"가 아니라 **"데이터 자산 + 기존 워크플로우
진입"**으로 재정의하는 것이 내부 설득력 측면에서도 유리합니다.

## 6. 산출물 형식 제안 (시나리오 카드)

```
────────────────────────────────────────────
 아이가 수족구에 걸렸을 때
────────────────────────────────────────────
 [현재 설계안에서 확인할 수 있는 담보]

 · 통원 치료를 받은 경우
     실손의료비(통원)        가입금액 5만원
     └ 약관상 조건: 통원 1회당 공제금액 차감 후 보상

 · 입원한 경우
     질병입원일당            가입금액 3만원
     └ 약관상 조건: 3일 초과 입원 시 4일째부터 지급

 [주의해서 안내할 사항]
 · 외래 진료만 받은 경우 입원 관련 담보는 해당하지 않습니다
 · 수족구는 별도 진단비 담보 대상에 포함되지 않는 경우가 많습니다
   (현재 설계안에는 해당 담보가 포함되어 있지 않습니다)

 ※ 실제 보험금 지급 여부 및 금액은 약관과 보험금 심사 결과에 따라
   결정됩니다.
────────────────────────────────────────────
```

**"설계안에 없는 담보"를 함께 보여주는 것**이 설계사 입장에서는 추가 제안의 근거가 되고,
고객 입장에서는 설명의 신뢰도를 높입니다. 이 항목을 카드 구성에 포함할 것을 제안합니다.

## 7. MVP 범위 제안

**태아·어린이보험 단일 라인으로 시작할 것을 권고합니다.** 기획안이 태아보험을 예시로 든 것은
적절한 선택이며, 근거는 다음과 같습니다.

- 발생 Event가 정형적이고 목록화가 용이함 (감염질환, 골절, 화상, 입원, 수술)
- 담보 수가 많아 설계사의 설명 부담이 가장 큰 영역 → 효용이 즉시 체감됨
- 판매량이 많아 사용 빈도 확보가 쉬움
- 고객(부모)의 이해 니즈가 가장 높음

| 단계 | 범위 | 산출물 |
| --- | --- | --- |
| 0 | 표준담보코드 체계 + Event 사전 구축 | 표준담보 100~150개, Event 15~20개 |
| 1 | 설계서 파싱 / 시스템 연동 | 담보·가입금액 추출 + 검증 UI |
| 2 | 담보 정규화 | 상위 3~5개사 대상 매핑 + 검수 |
| 3 | 약관 지급조건 연결 | 현행 판매 상품 약관 한정 |
| 4 | 시나리오 카드 생성 | 고정 템플릿 + 준법 심의 |
| 5 | 설계사 피드백 루프 | 오류 신고 → 매핑 보정 |

확장 순서는 `어린이·태아 → 종합보험(성인) → 기존 계약 보장분석` 을 권고합니다. 마지막 단계는
과거 약관 아카이브가 필요하므로 난이도가 다시 상승합니다.

## 8. 품질 평가 체계 (착수 시점에 함께 준비)

RAG 기반 서비스는 정답셋 없이 개선이 불가능합니다. 착수와 동시에 Golden Set 구축이 필요합니다.

- 구성: 실제 설계서 샘플 × Event 조합 200~300건, 각각의 기대 담보 목록과 지급조건을 사람이 확정
- **두 지표를 분리 관리할 것을 권고합니다.**
  - **누락률(재현율)** — 설계안에 있는데 시나리오에서 빠뜨린 담보. 설계사의 신뢰를 잃게 하는 요인
  - **오탐률(정밀도)** — 없는 보장을 있다고 안내. **컴플라이언스 사고로 직결되므로 허용치를
    0에 가깝게 관리**해야 하는 지표
- 두 지표는 트레이드오프 관계이므로, 불확실한 경우 "확인이 필요합니다"로 출력하도록 설계하여
  오탐을 누락 방향으로 흡수시키는 것이 안전합니다 (4-1의 `relation: 조건부` 필드의 용도)

## 10. 요약

- 4단계 방향은 타당하며, Event 중심 전환은 이 기획안의 가장 중요한 성과입니다.
- 다만 **담보 표준화**가 실질적 병목이며, 여기에 자원을 우선 배분해야 합니다.
- **가입설계서에 개인정보가 남아 있으므로** 무저장 처리 원칙을 설계에 명시해야 합니다.
- **자유 서술형 생성 대신 고정 템플릿**을 채택해야 준법 심의와 품질 관리가 모두 가능합니다.
- **"보장되지 않는 것"을 함께 안내**하는 것이 차별화이자 리스크 방어 수단입니다.
- 차별화 논리는 아이디어가 아니라 **데이터 자산과 워크플로우 진입점**으로 재정의하는 것이
  적절합니다.
