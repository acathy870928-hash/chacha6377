## 1. 사업 개요

### 1.1 목적

**FA가 선배 설계사나 지점장에게 확인하던 것을 대체한다.**

경쟁 상대는 다른 약관 검색 서비스가 아니라 *사람에게 묻는 방식*이다. 그 방식의 한계는 셋이다.
물어볼 수 있는 시간이 정해져 있고, 답이 사람에 따라 다르고, 묻는 쪽이 아쉬워진다.
이 시스템은 **24시간 · 같은 기준 · 근거 조항 제시**로 그 셋을 없앤다.

목적을 셋으로 압축한다.

| # | 목적 | 성공 기준 |
| --- | --- | --- |
| 1 | **보상 질문에 근거를 갖고 답한다** | 답변에 상품 · 약관 판 · 조항 위치가 함께 나온다 |
| 2 | **틀린 「나온다」를 만들지 않는다** | 면책 조항이 지급사유보다 먼저 판정 · 표시된다 |
| 3 | **쓸수록 고객 자료가 쌓인다** | 확인한 약관이 고객 폴더에 누적되어 되묻기가 줄어든다 |

가장 큰 효용은 **보상**에서 나온다. 지급 여부는 기억으로 답하기 가장 위험한 영역이고,
틀리면 FA가 고객에게 잘못 안내한 것이 된다.

### 1.2 답변 두 층 — 1차 범위의 경계

| | 1층 · 범용 (1차 오픈 범위) | 2층 · 초개인화 (2차) |
| --- | --- | --- |
| 근거 | Micky + 약관 | + 보장분석 |
| 답하는 것 | 담보 정의, 지급사유, **면책**, 감액 조건 | 「어디가 다쳤는데 얼마 받을 수 있어요」 |
| **금액** | **말하지 않는다** | 조건 넷이 모두 갖춰졌을 때만 |

금액을 말하려면 ① 보험사 · 상품 ② 가입 담보와 **가입금액** ③ 적용 약관 판
④ 지급사유 · 면책 조항이 모두 있어야 한다. 이 중 ①②는 보장분석에서만 온다.
1차 범위에 보장분석이 없으므로 **1차에서 금액 답변은 기능적으로 차단한다**(IA-AI-004).

### 1.3 이 사업이 기대고 있는 전제

착수 전에 깨질 수 있는 전제다. 9장에서 확인 항목으로 다시 다룬다.

- 약관 등록은 **유료**이며 과금 단위는 **약관 파일 건수**다. 단가는 **미확정**이다.
- 벤더 색인에 **판매 종료 상품**이 포함될 수 있어야 한다. 보상 질문은 과거 계약에서 나온다.
- 벤더 API가 **근거 청크(조항 원문)**를 함께 반환해야 한다. 반환되지 않으면 목적 1이 성립하지 않는다.

## 2. 현황 및 문제점

### 2.1 현재 업무

| 구분 | 현재 |
| --- | --- |
| 보상 질문 처리 | FA → 선배 설계사 · 지점장 · 보상팀에 구두 확인 |
| 약관 확인 | 보험사 공시실 · 모홈 등에서 PDF를 직접 열어 검색 |
| 기존 사내 AI | 출처 없는 일반론 답변. 「보통 …입니다」 수준에서 끝남 |
| 고객 계약 정보 | 보장분석 리포트(PDF)로 발행되나 **AI와 연결돼 있지 않음** |

### 2.2 문제점

**(1) 답이 사람과 시간에 묶여 있다.**
지점장이 자리에 없으면 답을 못 얻는다. 같은 질문에 답이 달라진다.

**(2) 기존 AI 답변에 근거가 없다.**
「펫보험은 보통 …를 보장합니다」는 FA가 고객에게 옮길 수 없다.
상품도 약관 판도 조항도 없어, 확인이 필요한 순간에 쓸 수 없다.

**(3) 약관 판을 사람이 관리할 수 없다.**
보상은 **계약 체결 시점의 약관**이 적용된다. 최신 약관으로 답하면 틀린 답이다.
그런데 한 상품의 판이 150개를 넘는 경우가 있고, 상품 하나가 보장형태 · 납입방법에 따라
파일 여러 건으로 갈린다. 사람이 눈으로 고를 수 있는 규모가 아니다.

**(4) 지급사유만 보고 판단하는 사고가 반복된다.**
조항만 보면 보상 가능해 보이지만 면책에 걸려 지급되지 않는 건이 있다.
현재는 이 확인이 개인의 숙련도에 달려 있다.

**(5) 약관 확보에 비용이 든다.**
약관은 벤더에 등록해야 검색되고, 등록은 유료다. 무엇을 살지 잘못 고르면 그대로 손실이다.
지금 가진 실적 데이터(손보 91개 · 61,297건, 생보 29개)는 *지금 파는 상품* 목록인데,
보상 질문은 *이미 가입한 계약*에서 나온다. 두 목록이 다르다.

### 2.3 제약사항

- **일정** — 착수부터 오픈까지 약 7주. 요구사항을 1차 필수와 2차로 갈라야 한다.
- **소스** — 1차는 Micky · VELUGA 2종뿐. 보장분석 · Cloud DATA · External MCP는 범위 밖.
- **생성 위치** — 답변 생성이 벤더 API 안에서 일어난다. 품질 통제 수단이 프롬프트 제어 가능 여부에 달려 있다.
- **단가 미확정** — 유료 확보 흐름에서 금액을 표시할 수 없다(4.2 참조).

## 3. 추진 범위

### 3.1 대상 업무

| 포함 | 제외 (2차 이후) |
| --- | --- |
| 보상 질문 응답 (지급사유 · 면책 · 감액) | 보험금 청구 접수 · 심사 |
| 담보 · 제도 · 용어 일반 질문 응답 | 수수료 · 실적 등 사내 시스템 조회(Cloud DATA) |
| 약관 판 특정 및 되묻기 | 고객 직접 사용 |
| 고객별 약관 누적(약관북) · 보장맵 | **금액 산출 · 초개인화**(보장분석 연동 후) |
| 미등록 약관 확보 요청 · 승인 · 검수 · 알림 | 청약 · 설계 · 상품 비교 |

### 3.2 대상 사용자

| 역할 | 하는 일 | 1차 |
| --- | --- | --- |
| **FA** | 질문, 고객 · 약관 등록, 확보 요청 | ✅ |
| **관리자** | 확보 요청 승인, 예산 집행, 품질 지표 확인 | ✅ (최소 기능) |
| 고객 | 본인 보장 확인 | ❌ 2차 |

### 3.3 1차 / 2차 경계

1차에서 **초개인화를 뺀다.** 대신 초개인화가 붙을 자리(보장맵의 「확인 필요」 상태,
보장분석 리포트 임포트 경로)를 1차에 만들어 두어 2차에 구조를 바꾸지 않는다.

```
1차 (10/1)   질문 → 라우팅 → 판 특정(되묻기) → 약관 검색 → 근거 조항 + 면책 우선 답변
                                                    ↓
                                    고객 · 약관 등록 → 약관북 · 보장맵(확인 필요 상태)
                                                    ↓
                                    미등록 → 확보 요청 → 승인 → 등록 → 검수 → 알림

2차          + 보장분석 연동 → 가입 담보 · 가입금액 확정 → 금액 답변(초개인화)
```

### 4.2 전 요구사항에 걸리는 공통 규칙

개별 요구사항에 반복해 쓰지 않고 여기 한 번만 적는다. **모든 상세 요구사항이 이 규칙을 만족해야 한다.**

| # | 규칙 | 근거 |
| --- | --- | --- |
| R1 | **면책이 먼저다.** 면책에 걸리면 지급사유가 있어도 뒤집지 못한다. 판정 순서도 화면 순서도 면책이 앞이다 | 지급사유를 먼저 보이면 FA가 그 줄에서 읽기를 멈춘다 |
| R2 | **판을 추측하지 않는다.** 가입 시점이 특정되지 않으면 최신 판으로 답하지 않는다 | 개정 전 가입자에게 틀린 답을 주는 것이 답을 못 하는 것보다 나쁘다 |
| R3 | **근거가 없으면 모른다고 답한다.** 검색 결과에 조항이 없으면 생성하지 않는다 | 없는 근거를 만드는 것이 가장 큰 사고다 |
| R4 | **약관의 담보 ≠ 가입한 담보.** 약관에는 가입 *가능한* 담보가 전부 들어 있다 | 약관만으로 「나온다」고 답하면 안 된다 |
| R5 | **1차에서 금액을 말하지 않는다.** 가입금액이 없으면 「가입했다면 얼마」조차 말하지 않는다 | 1.2 참조 |
| R6 | **면책 · 미가입에 0원을 쓰지 않는다.** 숫자가 아니라 사유를 둔다 | 0원은 계산 결과처럼 보이지만 지급 자체가 성립하지 않는 것이다 |
| R7 | **비용은 먼저 밝히고 동의를 받는다.** 단가 미확정 구간에서는 **요청 의사만** 받는다 | 금액을 모른 채 받는 동의는 백지 동의다 |
| R8 | **최종 판단자는 사람이다.** 답변은 확인이 필요한 쟁점을 짚고, 확정은 보상 심사로 넘긴다 | 금융분야 AI 가이드라인의 **보조수단성** 원칙 |
| R9 | **출처를 항상 표기한다.** Micky 근거와 약관 근거를 한 답변 안에서 구분한다 | 어느 문장이 약관 근거인지 FA가 알아야 한다 |
| R10 | **벤더에 개인정보를 보내지 않는다.** 질의는 보험사 · 상품 · 판 · 담보 · 상황 서술로 제한한다 | 8장 참조 |

### IA-FUN-001

| 분류 | 기능 | 고유번호 | IA-FUN-001 | 우선순위 | 1차 필수 | 담당 | iFA |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 질문 분류 및 소스 라우팅

**정의** FA의 질문을 유형별로 분류해 Micky · VELUGA 중 어느 소스를 쓸지, 약관 판 특정이 필요한지를 결정하는 기능

**요구사항**

- 질문을 8개 유형(개념 / 판매 / 상품정보 / 담보용어 / **보상** / 인수심사 / 절차 / 계약가치)으로 분류하여야 함
- 유형별로 사용할 소스와 **약관 판 민감도**(필수 / 선호 / 불필요)를 결정하여야 함
- 분류는 LLM이 수행하되 **라우팅 판단은 규칙 코드로 고정**하여야 함

**상세기술**

- 분류 결과는 구조화된 형태로 받는다: 질문유형, 상품 언급 여부, 시점 언급 여부, 특약 언급 여부, 담보 언급 여부, 약관 필요 여부, 판단 근거
- 라우팅 표는 코드 상수로 관리하며 LLM 출력에 좌우되지 않는다. LLM이 「약관이 필요 없다」고 해도 보상 유형이면 약관 경로로 간다
- 판 민감도가 **필수**인 유형(보상 · 담보용어 일부)은 판이 특정되지 않으면 검색을 실행하지 않고 되묻기(IA-FUN-002)로 넘긴다
- **담보 지목 범위**를 함께 판별한다
  - *지목형* — 「골절진단비 나오나요」처럼 담보가 명시된 질문 → 해당 담보만 조회
  - *열거형* — 「골절됐는데 보상되나요」처럼 상황만 있는 질문 → **걸릴 수 있는 담보를 모두 열거**한다. 좁게 잡으면 청구 누락이 생기므로 넓게 걸고 FA가 판단하게 한다

- 분류 실패 · 저확신 시 임의 라우팅하지 않고 일반 경로 + 되묻기로 처리한다

**산출정보** 라우팅 정의서, 질문유형 분류 기준서, 분류 프롬프트 명세, 라우팅 단위테스트 결과서

### IA-FUN-002

| 분류 | 기능 | 고유번호 | IA-FUN-002 | 우선순위 | 1차 필수 | 담당 | iFA |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 약관 판(edition) 특정 및 되묻기

**정의** 보상 질문에 적용할 약관 판을 계약 시점 기준으로 확정하고, 확정되지 않으면 최소 횟수로 되물어 좁히는 기능

**요구사항**

- 보상 답변은 **계약 체결 시점에 시행 중이던 판**을 기준으로 하여야 함. 최신 판을 임의로 적용하여서는 안 됨
- 판이 확정되지 않은 경우 보험사 → 상품 → 가입 시점 순으로 되물어야 함
- 이미 확정된 정보는 다시 묻지 않아야 함 (세션 컨텍스트 · 약관북 · 보장맵 우선 조회)

**상세기술**

- **되묻기는 걸러낸 뒤에만 한다.** ① 세션에 이미 있음 ② 고객 폴더에 해당 계약이 있음 ③ 판이 하나뿐임 — 셋 중 하나면 묻지 않는다
- **가입 시점은 「연 · 월」까지만 받는다.** 약관 시행일이 대개 매월 1일이고 개정이 분기 · 반기 시작일에 몰리므로, 연 · 월만으로 판이 확정되는 경우가 대부분이다. 월 경계에 걸쳐 판이 2개 이상 남을 때만 일자를 추가로 묻는다
- **판 후보가 6개 이하일 때만 칩(버튼)으로 제시**한다. 한 상품에 판이 150개를 넘는 경우가 있어 전량 나열이 불가능하므로, 초과 시에는 연 · 월 입력만 받는다
- 상품 후보가 8개를 넘으면 상품을 나열하지 않고 **보험사부터 좁힌다**
- 상품명은 자유 입력을 받되 **선택은 목록에서** 하게 한다. 자유 입력만 받으면 표기가 흔들려 같은 약관에 대한 요청이 여러 건으로 흩어진다
- 상품명 정규화 시 배당 표기(무배당 등)만 걷어내고 **괄호 안 보장형태 · 납입방법 표기는 유지**한다. 「동행(사망보장형-월납)」과 「동행 Plus(월납)」은 약관 파일이 다르다
- 이름이 정확히 일치해도 후보를 단독 확정하지 않는다(「동행」과 「동행 Plus」가 함께 존재)
- 되묻기 선택지에 **미등록 상품도 포함**하고 「약관 준비중」으로 표시한다. 목록에 아예 없으면 FA는 상품명을 잘못 말한 것인지 자료가 없는 것인지 구분하지 못한다

**산출정보** 되묻기 흐름도, 판 해석 규칙 정의서, 상품명 정규화 규칙서, 화면정의서, 단위테스트 결과서

### IA-FUN-003

| 분류 | 기능 | 고유번호 | IA-FUN-003 | 우선순위 | 1차 필수 | 담당 | iFA |

**명칭** 보상 판정 — 면책 우선

**정의** 검색된 조항을 근거로 지급 가능성을 판정하되, 면책 조항을 지급사유보다 먼저 평가하는 기능

**요구사항**

- 판정 순서는 **① 가입 여부 → ② 면책 → ③ 지급사유 → ④ 감액 · 대기기간 · 한도**로 고정하여야 함
- 면책에 해당하면 지급사유 조항이 있어도 지급 가능으로 판정하여서는 안 됨
- 판정 결과를 답변 **최상단**에 배치하여야 함

**상세기술**

- 판정 결과 구분: `지급가능` / `감액·조건부` / `면책` / `미가입` / `사실확인필요` / `불명`
- 사실관계에 따라 면책 여부가 갈리는 건(예: 음주 여부, 업무 중 여부)은 `면책`으로 단정하지 않고 **`사실확인필요`**로 표시하고 확인해야 할 사실을 명시한다
- 근거 조항이 하나도 없으면 `불명`이며, 「지급되지 않는다」로 바꾸어 표시하지 않는다. **근거 없음과 지급 불가는 다르다**
- **면책 · 미가입 건의 금액 자리에 0원을 쓰지 않는다.** 0원은 계산 결과처럼 보이지만 지급 자체가 성립하지 않는 것이므로 사유를 표시한다
- 합계는 `지급가능` 건만 합산하고, 합산에서 제외된 건수와 사유를 함께 표시한다
- **막힌 건도 숨기지 않는다.** 면책 · 미가입 · 확인 필요 건을 목록에서 빼면 FA가 다시 확인해야 한다
- 지급사유를 먼저 보여주지 않는다. FA가 그 줄에서 읽기를 멈추면 아래 면책이 읽히지 않는다

**산출정보** 판정 로직 명세서, 판정 결과 표기 가이드, 화면정의서, 판정 단위테스트 결과서

- 상담이 끝나면 세션 컨텍스트를 내린다. 다른 고객 데이터로 답하고 있는 것을 아무도 모르는 상태를 만들지 않는다

### IA-FUN-005

| 분류 | 기능 | 고유번호 | IA-FUN-005 | 우선순위 | 1차 필수 | 담당 | iFA |

**명칭** 약관 등록 — 다중 경로

**정의** 고객의 가입 계약을 보장맵에 등록하는 기능. 상황에 따라 빠른 경로를 우선 제시한다

**요구사항**

- 등록 경로를 **최소 4종** 제공하고 **빠른 순으로 정렬**하여 제시하여야 함
- 현재 상황에서 사용할 수 없는 경로는 목록에서 제외하여야 함
- 등록 후 **다른 상품 추가 등록**을 이어서 유도하여야 함

**상세기술**

- 보험사 → 상품 검색 → 등록만 제공하면 한 건에 3단계이고, 고객 한 명이 계약을 대여섯 건 보유하므로 **15단계**가 된다. FA는 한 번 해보고 다시 하지 않는다. 경로를 늘리는 이유가 여기 있다

  | 순 | 경로 | 특징 |
  | --- | --- | --- |
  | 1 | **보장분석 리포트 파일 업로드** | 계약 전부가 한 번에. FA가 이미 발행받아 가지고 있는 문서다 |
  | 2 | **대화에서 말한 상품 등록** | 이미 말한 상품을 다시 검색하게 하지 않는다 |
  | 3 | **최근 등록한 상품에서 선택** | 인기 상품은 고객마다 겹친다(손보 실적 상위 10개 중 7개가 운전자보험) |
  | 4 | 보험사 · 상품명 검색 | 확실하지만 느리다. 마지막 수단 |

- 경로 1은 **보장분석 *연동*(2차) 없이도 *파일*로 동작한다.** 리포트에 계약별 보험사 · 상품명 · 계약년월이 들어 있다
- 업로드 결과는 **저장 전에 확인 화면**으로 보여준다. 파일에서 잘못 읽힌 계약이 확인 없이 보장맵에 남으면 안 된다
- 확인 화면은 전체 선택 상태로 시작하되 개별 해제가 가능해야 한다(해지 계약 · 무관한 계약 제외)
- **「계약을 확인한 것」과 「약관이 등록된 것」을 목록에서 구분 표시**한다. 이 구분을 숨기면 보장맵은 채워진 것처럼 보이는데 정작 답을 못 한다. 약관 미등록 건은 IA-FUN-008로 이어진다
- 요약 문구에 등록 건수와 **약관 확보 필요 건수를 함께** 표기한다

**산출정보** 화면정의서, 리포트 파서 명세서, 업로드 파일 형식 · 용량 · 검증 규칙서, 사용자 매뉴얼

**명칭** 보장맵

**정의** 등록된 약관을 고객 → 계약 → 담보 3계층으로 펼쳐 보여주고, 담보별 가입 상태를 관리하는 기능

**요구사항**

- 확정 근거(증권 확인 / 보장분석 / 수기)를 담보별로 보관하여야 함

**상세기술**

- 약관은 그 상품에서 **가입할 수 있는** 담보의 목록일 뿐이므로, 약관만 등록한 상태를 가입으로 취급하면 안 된다(R4)

- 답변에서 확인 필요 건은 합계에서 제외하되 **몇 건인지 밝힌다**

- 확정 비율과 부족 항목 요약을 제공해 무엇을 더 확인해야 하는지 보이게 한다
- 명칭은 「보장트리」(개발 용어) · 「보장분석」(보장분석 업체 서비스명과 충돌)을 쓰지 않는다. **「보장맵을 채운다 · 비어 있다」로 미완성 상태를 말할 수 있다는 점**이 이 이름을 고른 이유다

**산출정보** 화면정의서, 보장맵 데이터 모델 정의서, 담보 상태 전이 규칙서

### IA-FUN-007

**명칭** 약관북 — 고객별 폴더

**정의** 상담 중 확인한 약관을 고객별 폴더로 누적하고, 다음 상담에서 되묻기 없이 다시 열 수 있게 하는 기능

**요구사항**

- 답변에 사용한 약관을 **고객 건으로 지정해 누적**할 수 있어야 함
- 약관북은 상담과 **나란한 최상위 메뉴**여야 하며, 첫 화면은 질문창이어야 함
- 폴더를 열고 질문하면 되묻기 없이 그 계약 기준으로 답하여야 함

**상세기술**

- 「최근 상담」(대화 이력)과 약관북(고객별 약관)은 성격이 다르므로 같은 목록에 섞지 않는다
- 폴더 정렬은 **약관이 최근에 추가된 순**. 상담이 이어지는 고객이 위에 있어야 다시 여는 동작이 빨라진다
- 검색은 **고객명과 상품명 양쪽**으로 되어야 한다. FA는 「누구 폴더」로도 찾지만 「그 어린이보험 어디 있더라」로도 찾는다
- 같은 고객 · 같은 약관은 중복 저장하지 않는다
- 연결 출처(상담 중 저장 / 보장분석 / 유료 확보)를 보관해 **비용을 들여 확보한 약관이 몇 명에게 쓰이는지** 집계할 수 있게 한다
- 상담 제목에 상품 · 판을 남긴다(예: 「차○희 · 골절 진단금 / 내맘같은어린이보험 2019.04 판」). 어떤 기준으로 답했는지가 이력에 남아야 나중에 되짚을 수 있다

**산출정보** 화면정의서, 데이터 모델 정의서, 검색 사양서

### IA-FUN-008

**명칭** 미등록 약관 확보 요청 및 비용 동의

**정의** 벤더에 색인되지 않은 약관을 FA가 확보 요청하고, 비용 부담에 동의하는 절차

**요구사항**

- 미등록 약관이어도 **상품과 가입 시점을 먼저 확정한 뒤** 요청을 접수하여야 함
- 비용이 발생할 수 있음을 **접수 전에** 고지하고 동의를 받아야 함
- 동일 상품 · 동일 판에 대한 선행 요청이 진행 중이면 **중복 과금하지 않아야** 함

**상세기술**

- **단가 미확정 구간의 처리(현재 상태)** — 금액을 표시하지 않고 **요청 의사만** 받는다

  > 「…확보에는 등록 비용이 발생할 수 있습니다. 요청을 남기시면 비용과 진행 여부를 확인해 안내드리겠습니다.」 `[확보 요청하기]` `[취소]`

  접수된 요청은 *청구 대상 후보*이지 결제 동의가 아니다. 실제 청구는 금액을 안내하고 **다시 동의를 받은 뒤에만** 한다. 단가가 확정되면 「요청하기 (30,000원)」 형태의 확정 동의 흐름으로 전환한다

- 고지 화면에 ① 무엇에 대한 비용인지(상품명 + 판/시행일까지) ② 금액 ③ **취소**를 항상 함께 둔다
- 미등록이어도 되묻기를 끝까지 하는 이유는 등록 단위가 「상품」이 아니라 **「상품 + 판」**이기 때문이다. 상품명만으로는 어느 판을 살지 정해지지 않는다
- 요청은 세 갈래로 처리한다

  | 상황 | 처리 |
  | --- | --- |
  | 색인에 있음 | 판 특정 후 검색 · 답변 |
  | 마스터에 있으나 미색인 | 시점 확인 → 없다고 안내 + 요청 기록(상품 ID 포함) |
  | 마스터에도 없는 이름 | 시점 확인 → 없다고 안내 + 요청 기록(이름만) |

  세 번째를 「모르는 상품입니다」로 끝내지 않는다. 그렇게 하면 우리가 모르는 상품일수록 요청이 쌓이지 않아 정작 필요한 약관이 등록 목록에 영영 오르지 않는다

- **요청 시점의 원 질문을 함께 저장**한다. 검수(IA-FUN-009)와 알림에 그대로 쓴다
- 「확보 대상으로 등록했습니다」처럼 **등록을 약속하지 않는다.** 「접수했고 검토 후 안내」까지만 말한다

**산출정보** 화면정의서, 비용 고지 문안, 요청 상태 전이 정의서, 과금 정책서(정책 확정 후)

### IA-FUN-009

| 분류 | 기능 | 고유번호 | IA-FUN-009 | 우선순위 | 1차 필수 | 담당 | 공통 |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 확보 파이프라인 · 검수 · 알림

**정의** 접수된 요청을 약관 확보 → 색인 → 검수 → 알림까지 처리하는 운영 흐름

**요구사항**

- 상태를 `접수 → 대기 → 확보 → 색인 → 검수 → 알림`으로 관리하고 각 단계 전이를 기록하여야 함
- **검수를 통과한 뒤에만** 완료 알림을 발송하여야 함
- 확보 실패 시에도 사유와 함께 종료를 알려야 함

**상세기술**

- **임베딩이 끝난 것과 답할 수 있는 것은 다르다.** 파일 파싱 오류, 특약 미구분, 판 오매핑이 있으면 등록은 됐는데 답이 안 나온다. 이 상태에서 「등록됐습니다」를 알리면 FA가 다시 물어보고 또 실패한다 — 신뢰가 한 번에 깨진다
- 그래서 검수 기준을 「임베딩 성공」이 아니라 **「그 FA의 원 질문에 근거 조항이 나오는가」**로 둔다. 저장해 둔 원 질문을 그대로 재실행한다
- 검수 통과 조건에 **면책 조항이 함께 검색되는지**를 포함한다. 지급사유는 잘 찾는데 면책을 놓치는 색인은 가장 나쁜 형태로 틀린다
- 알림 규칙
  - **원 질문을 알림에 함께 싣고** 탭 한 번으로 그 맥락으로 돌아가게 한다. 「요청하신 약관이 등록되었습니다」만 보내면 며칠 뒤 FA는 자신이 무엇을 물었는지 기억하지 못한다
  - 같은 FA · 같은 약관은 여러 번 물었어도 **1회만** 알린다
  - 배치에서 여러 약관이 동시에 등록되면 **FA별로 묶어 한 건**으로 보낸다. 100건 배치 후 알림이 폭주하면 알림 자체가 무시된다
  - **접수 즉시** 「접수했습니다」를 보여준다. 완료 알림만 있으면 요청 직후의 FA는 실패한 것으로 받아들인다

- 배치 주기는 **주 1회 고정**. 주기가 일정해야 예상 시점을 안내할 수 있다
- 약관 개정 알림(새 판 시행 시 해당 상품을 자주 조회한 FA에게 통지)은 2차. 개정이 분기 시작일에 몰리므로 **분기 점검**으로 충분하다

**산출정보** 업무흐름도, 상태 전이 정의서, 검수 체크리스트, 알림 템플릿 목록, 배치 운영 절차서

- 자료 유효기간이 지난 문서가 검색 결과에 섞이지 않아야 함

**상세기술**

- 「골절이 되었는데 보상될 수 있어요?」는 Micky만으로 답이 나오고 **그 답으로 충분한 경우가 많다.** 매번 약관 등록을 요구하면 도구가 무거워진다
- 답변 하단에 개인화 분기를 둔다 — `[고객 약관 등록하고 확인하기]` / `[이 답변으로 충분해요]`. **두 선택지를 같은 무게로** 둔다. 일반 답변은 실패가 아니다
- 이미 계약 기준으로 답한 상담(약관북에서 열고 들어온 경우 등)에서는 분기를 띄우지 않는다
- 자료 유효기간 · 태그 체계는 AX팀 공유 예정(TBD). 인덱스 단계에서 만료 자료를 거르는 구조를 먼저 만들어 둔다

**산출정보** 지식베이스 목록, 유효기간 · 태그 정책서, 인덱싱 파이프라인 명세서

| **개인정보 보호법 제37조의2** (자동화된 결정 관련 권리) | 본 서비스는 **완전히 자동화된 결정을 하지 않는다.** 지급 여부는 보험사 보상 심사가 결정하고 본 서비스는 조항을 제시할 뿐이다. 이 경계를 답변 문구로 명시한다 |
| 개인정보 보호법 · 신용정보법 | 최소수집 · 목적 제한 · 위탁 · 국외이전 (IA-SEC-001) |
| 보험업법 · 금융소비자보호법 | FA가 고객에게 전달할 때의 설명 책임은 FA에게 있다. 답변에 **확정 표현을 쓰지 않는다** |
| 보험업감독규정 · 시행세칙 | 상품공시 통일 양식이 상품 · 판 마스터의 원천 근거다(IA-DAT-001) |

- 법령 해석과 동의 범위 판단은 **법무 검토 대상**이며 본 문서의 판단이 아니다(9.3)

**산출정보** 규정 준수 점검표, AI 서비스 성격 정의서(고영향 해당 여부 검토 자료), 법무 검토 결과서

| 분류 | 제약사항 | 고유번호 | IA-CON-002 | 우선순위 | 1차 필수 | 담당 | iFA |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 1차 범위 제약 — 소스 2종 · 금액 미답변

**정의** 1차 오픈에서 의도적으로 제외하는 범위와 그 처리 방식

**요구사항** 범위 밖 질문에 **추정으로 답하지 않고 경계를 안내**하여야 함

**상세기술** 소스는 Micky · VELUGA 2종뿐이다. 수수료 · 실적 · 계약 조회(Cloud DATA), 외부 자료(External MCP), 사내 규정(BumE_F)은 연결되지 않았으므로 「지금은 답할 수 없다」고 안내한다. **연결 안 된 소스의 답을 일반지식으로 지어내지 않는다.** 금액 미답변은 R5. 이 제약들은 2차에서 해제되므로 코드에서 **설정으로 분리**해 둔다

**산출정보** 범위 정의서, 경계 안내 문구집

## 9. 전달 전 확인해야 할 정보

이 문서를 벤더 · 내부에 전달하기 전에 채워야 하는 값이다. **9.1은 채워지지 않으면 계획 자체가 흔들린다.**

### 9.1 벤더(VELUGA)에 받아야 할 값 — 우선순위 순

| # | 항목 | 왜 먼저인가 |
| --- | --- | --- |
| 1 | **판매 종료 상품 색인 가능 여부** | 불가하면 보상용 약관을 살 수 없다. **이 기획의 전제가 무너진다.** 늦게 알수록 되돌리기 어렵다 |
| 2 | **약관 파일 1건당 단가와 과금 단위** | 판당 / 용량 / 구간 정액 중 무엇인지에 따라 등록 전략이 전부 달라진다. 화면에 금액을 표시할 수 있는지도 여기서 정해진다 |
| 3 | **상품당 약관 파일 수(배수)** | 「동행」 하나의 실제 약관 목록만 받아도 배수가 나온다. 배수 6이면 200파일에 손보 상품이 4개만 들어간다 |
| 4 | **판도 파일 수에 곱해지는가** | 곱해지면 실손 계열(판 150개 초과)은 전량 등록이 불가능하고 부분 등록 전략으로 가야 한다 |
| 5 | 근거 청크 반환 여부 | 반환 안 되면 근거 조항을 제시할 수 없다 — 목적 1 불성립 |
| 6 | 프롬프트 · 답변 형식 제어 가능 여부 | 면책 우선 표시를 우리가 강제할 수 있는지 |
| 7 | retrieval-only 모드 유무 | 있으면 Micky와 합쳐 우리가 직접 생성하는 선택지가 열린다 |
| 8 | 멀티턴 지원 여부 | 되묻기 후 대화 연결 방식이 갈린다 |
| 9 | 청크 메타데이터 실측 (IA-DAT-002 표) | **특약 구분이 가장 중요** |
| 10 | 색인 커버리지 · 갱신 주기 | 초기 등록 목록 산정 |
| 11 | 선택 가능 모델 · 비용 · 지연, 인증 · 호출 한도 | 성능 · 비용 산정 |

### 9.2 내부에서 확정해야 할 값

| 항목 | 필요한 것 | 미확정 시 |
| --- | --- | --- |
| **초기 등록 목록** | 회사 부담분(200파일 상당)에 무엇을 넣을지 | 실적 목록(현재 판매 상품)으로만 채우면 **영업용 약관을 사고 보상 질문은 못 덮는다** |
| **1차 오픈 종목** | 운전자보험 단독 권장 — 실적 상위 10개 중 7개, 담보 표준화, 판이 적다. 실손은 마지막 | 전 종목을 얕게 열면 품질 검증이 불가능하다 |
| **선구매 부담 분담** | 먼저 요청한 FA가 뒤따르는 FA 몫까지 부담하는 구조를 둘지 | 자주 쓰이는 약관일수록 처음 요청자만 돈을 낸다 |
| **환불 조건** | 확보 실패 외에 검수 미통과도 환불 대상인지 | 요청자 책임이 아닌 실패에 과금된다 |
| **FA 1인당 월 요청 한도** | 둘지 말지 | 소수 FA가 예산을 크게 소진할 수 있다 |
| **파일 원본 보관** | 업로드한 리포트 원본을 남길지 · 얼마나 | 보관 책임이 정의되지 않는다 |
| **알림 채널** | 사내 메신저 / 알림톡 / 이메일 / 인앱 | IA-INT-005 산정 불가 |

### 9.3 법무 검토가 필요한 것 — 설계로 해결되지 않는다

1. **동의 범위** — 고객이 보장분석에 동의할 때의 이용 목적에 「AI 상담 지원」이 포함되는가. 리포트 발행까지만 동의했다면 목적이 추가된 것이다
2. **보관 기간** — 리포트 조회 시점 데이터를 얼마나 보유할 것인가
3. **제3자 제공 / 처리위탁** — 벤더에 나가는 값이 개인정보가 아니라는 판단의 확인. IA-SEC-001의 전송 항목 표가 근거 자료다
4. **마이데이터 사업자 계약** — 보장분석 발행 업체와의 계약에 2차 활용(AI 상담) 범위가 어떻게 되어 있는가
5. **고객 열람 · 삭제 요구** — 세션 · 저장소 · 로그에서 어떻게 지울 것인가
6. **고영향 AI 해당 여부** — 본 서비스가 AI 기본법상 고영향 AI에 해당하는지, 해당 시 이행 사항

> **동의 범위가 확인되기 전에도 1차는 진행할 수 있다.** 1차 범위에 보장분석 연동이 없고,
> 리포트는 FA가 직접 올리는 파일이며, 저장 없이 **세션에서만 쓰는 방식**을 선택할 수 있다.
> 등록 목록 산출용 집계는 개인을 식별하지 않는 형태(보험사 + 상품 + 계약년월 + 건수)로만 쌓는다.

### 9.4 규모 · 검수 기준

| 항목 | 값 |
| --- | --- |
| 대상 FA 수 · 피크 동시접속 | **[확정 필요]** |
| 초기 등록 파일 예산 | 200파일 상당(회사 부담) — 상품 수 환산은 배수 확정 후 |
| 검수 기준 | UAT 주요 시나리오 95% 이상 통과, 치명 결함 0건 |
| **오픈 조건** | **면책 재현율 100%** + 판 일치율 100% + 특약 오귀속 0건 + 근거 없는 단정 0건 |

## 10. 오픈 판정 — 무엇이 되면 여는가

7주 안에 전부 완성되지 않을 수 있다. **무엇이 안 되면 열지 않는지**를 먼저 정한다.

### 열지 못하는 조건 (하나라도 걸리면 연기)

- 골든셋에서 **면책 조항을 놓치는 답변이 1건이라도** 나온다
- 다른 판 · 다른 특약의 조항을 근거로 답한다
- 근거 없이 지급 가능 · 불가를 단정한다
- 담당하지 않는 고객의 자료가 조회된다
- 벤더 API 전송 값에 개인 식별정보가 포함된다

### 없어도 여는 것 (2차로 넘김)

- 관리자 승인 화면(IA-FUN-010) — 운영자 수기 처리로 대체
- 보장분석 API 연동(IA-DAT-003) — 파일 업로드만으로 시작
- 금액 답변(초개인화) — 애초에 1차 범위 밖
- 약관 개정 알림 — 분기 점검으로 대체
- 외부 알림 채널 — 인앱 알림만으로 시작

### 축소해서 여는 것

- **종목을 운전자보험으로 좁혀 연다.** 전 종목을 얕게 여는 것보다, 한 종목에서 「FA가 고객에게 그대로 읽어줄 수 있는 수준」을 만드는 편이 낫다
- 확보 요청은 **요청 의사만 받는 형태**로 연다(단가 확정 전)
