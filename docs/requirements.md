## 1. 사업 개요

### 1.1 목적

**FA가 선배 설계사나 지점장에게 확인하던 것을 대체한다.**

경쟁 상대는 다른 약관 검색 서비스가 아니라 *사람에게 묻는 방식*이다. 그 방식의 한계는 셋이다.
물어볼 수 있는 시간이 정해져 있고, 답이 사람에 따라 다르고, 묻는 쪽이 아쉬워진다.
이 시스템은 **24시간 · 같은 기준 · 근거 조항 제시**로 그 셋을 없앤다.

목적을 셋으로 압축한다.

| # | 목적 | 성공 기준 |
| --- | --- | --- |
| 1 | **어느 약관으로 답했는지가 항상 보인다** | 모든 답변에 보험사 · 상품 · 판 · 조항 위치가 함께 나온다 |
| 2 | **틀린 「나온다」를 만들지 않는다** | 면책 조항이 지급사유보다 먼저 판정 · 표시된다 |
| 3 | **쓸수록 고객 자료가 쌓인다** | 확인한 약관이 고객 폴더에 누적되어 되묻기가 줄어든다 |

가장 큰 효용은 **보상**에서 나온다. 지급 여부는 기억으로 답하기 가장 위험한 영역이고,
틀리면 FA가 고객에게 잘못 안내한 것이 된다.

### 1.2 답변 두 층 — 1차 범위의 경계

| | 1층 · 범용 (1차) | 2층 · 초개인화 (2차) |
| --- | --- | --- |
| 근거 | Micky + 약관 | + 보장분석 |
| 답하는 것 | 담보 정의, 지급사유, **면책**, 감액 조건 | 「어디가 다쳤는데 얼마 받을 수 있어요」 |
| **금액** | **말하지 않는다** | 조건 넷이 모두 갖춰졌을 때만 |

금액을 말하려면 ① 보험사 · 상품 ② 가입 담보와 **가입금액** ③ 적용 약관 판
④ 지급사유 · 면책 조항이 모두 있어야 한다. ①②는 보장분석에서만 온다.
1차 범위에 보장분석이 없으므로 **1차에서 금액 답변은 기능적으로 차단한다**(IA-AI-005).

## 2. 현황 및 문제점

### 2.1 현재 업무

| 구분 | 현재 |
| --- | --- |
| 보상 질문 처리 | FA → 선배 설계사 · 지점장 · 보상팀에 구두 확인 |
| 약관 확인 | 보험사 공시실 · 모홈 등에서 PDF를 직접 열어 검색 |
| 기존 사내 AI | 출처 없는 일반론 답변. 「보통 …입니다」 수준에서 끝남 |
| 고객 계약 정보 | 보장분석 · My Data로 확인 가능하나 **AI와 연결돼 있지 않음** |

### 2.2 「약관을 넣어두면 답한다」가 약관에서는 성립하지 않는다

**이 사업의 설계 전체가 이 문제 하나에서 나온다.** 여기를 건너뛰면 나머지 요구사항이
왜 이렇게 생겼는지 설명되지 않으므로 먼저 적는다.

**(1) 사람은 「어느 약관인지」를 먼저 확정한다.**
베테랑 담당자는 조항을 찾기 전에 「그거 참좋은동행이요? 2109 개정 맞죠?」를 먼저 묻는다.
확정되기 전에는 조항을 찾지 않고, 확정이 안 되면 **답을 지어내지 않고 되묻는다.**
그다음 그 약관 **한 권만** 펼치고, 한 권 안에서는 조항끼리 헷갈리지 않는다.

**(2) 그런데 일반적인 방식에는 그 1단계가 없다.**
약관 100권을 페이지 단위로 잘라 한 통에 섞어두고, 질문과 닮은 페이지를 골라 답을 만든다.
사람으로 치면 책장을 보지 않고 뜯어놓은 페이지 더미에 손을 넣어 더듬는 것이다.

| | 찾는 범위 |
| --- | --- |
| 사람의 방식 | 책장에서 그 책을 뽑는다 → 펼친다 → 찾는다 — **1권** |
| 그냥 넣어둔 방식 | 100권을 섞은 더미에서 닮은 페이지를 찾는다 — **100권 전부** |

**(3) 같은 조건을 사람에게 주면 사람도 못 한다.**
약관 100권의 표지를 떼고, 본문에서 상품명을 지우고, 페이지를 찢어 섞은 뒤
「계단에서 굴러 골절됐는데 보장돼요?」라고 물으면 30년 차도 못 맞춘다.
**능력의 문제가 아니라 조건의 문제다. 조건을 바꾸면 된다.**

**(4) 왜 하필 약관인가 — 서로 80~90%가 똑같은 책들이다.**
상품마다 다른 부분은 10~20%뿐이다. 검색이 하는 일은 「닮은 것 찾기」인데
대상이 전부 닮아 있으면 아무거나 집어온다. 쌍둥이 100명 중에서 닮은 사람을 찾으라는 것과 같다.

| 문서 종류 | 문서끼리 얼마나 다른가 | 넣어두면 답하는가 |
| --- | --- | --- |
| 사내 규정 · 매뉴얼 | 각자 완전히 다름 | 잘 됨 |
| 뉴스 · 리포트 | 주제가 전부 다름 | 잘 됨 |
| 계약서(건별) | 당사자 · 금액이 다름 | 대체로 됨 |
| 제품 매뉴얼(모델별) | 일부 겹침 | 주의 필요 |
| **보험 약관** | **서로 80~90% 동일** | **안 됨** |

**약관을 1,000권 넣어도 좋아지지 않는다. 오히려 나빠진다** — 닮은 것이 더 많아진다.
데이터를 더 넣어서 해결되는 종류의 문제가 아니다.

**(5) 가장 위험한 것 — 검색은 「모르겠다」를 출력할 수 없다.**
사람은 모르면 「어느 상품이에요? 확인해보고 알려드릴게요」라고 말한다.
검색은 구조상 후보를 점수순으로 내놓게 되어 있어, **100권이 다 닮아도 1등은 반드시 나온다.**
그리고 그 1등으로 「상해 9급에 해당하여 50만원이 지급됩니다」라고 자신 있게 답한다.

> **틀렸을 때 틀렸다는 신호가 어디에도 남지 않는다.**
> 약관에서는 「80점짜리 답」이 「답 없음」보다 위험하다.
> 보장 여부와 지급 금액은 민원 · 분쟁으로 직결된다.

**(6) 해결은 사람이 하던 순서를 그대로 시키는 것이다.** 새로 발명하는 것이 아니다.

```
1단계  어느 약관인지 확정한다      ← AI가 추측하지 않는다. 사용자가 고르거나 계약정보로 정해진다
2단계  그 약관 한 권만 펼친다      ← 확정된 1권 안에서만 찾는다
3단계  정해진 순서로 확인한다      ← 8칸 체크리스트. 면책을 건너뛸 수 없게 만든다
4단계  근거와 함께 답한다          ← 「제5조 제2항에 따라 …」 + 못 찾은 항목은 「해당 조항 없음」
```

요구사항 IA-FUN-001 · IA-AI-002 · IA-FUN-004 · IA-AI-001이 각각 이 네 단계에 대응한다.

### 2.3 나머지 문제점

**(1) 답이 사람과 시간에 묶여 있다.** 지점장이 자리에 없으면 답을 못 얻고, 같은 질문에 답이 달라진다.

**(2) 약관 판을 사람이 관리할 수 없다.** 보상은 **계약 체결 시점의 약관**이 적용된다.
최신 약관으로 답하면 틀린 답이다. 그런데 한 상품의 판이 150개를 넘는 경우가 있고,
상품 하나가 보장형태 · 납입방법에 따라 파일 여러 건으로 갈린다.

**(3) 지급사유만 보고 판단하는 사고가 반복된다.** 조항만 보면 보상 가능해 보이지만
면책에 걸려 지급되지 않는 건이 있다. 지금은 이 확인이 개인의 숙련도에 달려 있다.

**(4) 약관 확보에 비용이 든다.** 약관은 벤더에 등록해야 검색되고 등록은 유료다.
지금 가진 실적 데이터(손보 91개 · 61,297건, 생보 29개)는 *지금 파는 상품* 목록인데,
보상 질문은 *이미 가입한 계약*에서 나온다. 두 목록이 다르다.

### 2.4 제약사항

- **일정** — 착수부터 오픈까지 약 7주. 요구사항을 1차와 2차로 갈라야 한다.
- **소스** — 1차는 Micky · VELUGA 2종뿐. 보장분석 · Cloud DATA · External MCP는 범위 밖.
- **생성 위치** — 답변 생성이 벤더 API 안에서 일어난다. 품질 통제 수단이 프롬프트 제어 가능 여부에 달려 있다.
- **단가 미확정** — 유료 확보 흐름에서 금액을 표시할 수 없다(IA-FUN-009).

### 3.3 단계 구조 — 스코프를 좁히는 수단을 늘려간다

한 번에 다 만들지 않는다. **각 단계가 그 자체로 쓸모가 있다.**

| | 확보하는 것 | 가능해지는 것 | 클릭 |
| --- | --- | --- | --- |
| **1차** FA 직접 선택<br>보험사 → 상품 검색 → 판 | 약관 1권 확정 | 조항 조회 · 면책 확인 | 2~3번 |
| **2차** 계약 연동<br>증권 · 상품코드 · 계약일자 | 약관 자동 확정 | 「내 보험」 기준 답변 | 0회 |
| **2차** 보장분석 결합<br>담보 · 특약 단위 데이터 | 가입 담보 · 보장금액 | 금액 즉답 · 보장공백 | — |

마지막 단계에 오면 **질문의 상당수가 약관 검색을 아예 타지 않는다.**
「얼마 나와요?」는 보장 데이터 조회만으로 답하고, 약관은 「왜 그런가 · 면책은 없나」를
확인할 때만 펼친다. 어려운 문제를 푸는 대신 **그 문제를 만나는 횟수를 줄이는 구조**다.

**1차만 해도 지금보다 낫고, 뒤 단계가 늦어져도 서비스는 그대로 돈다.**

### 4.2 전 요구사항에 걸리는 공통 규칙

개별 요구사항에 반복해 쓰지 않고 여기 한 번만 적는다. **모든 요구사항이 이 규칙을 만족해야 한다.**
R1~R4가 2.2에서 나온 규칙이고, 나머지는 보상 답변의 안전 규칙이다.

| # | 규칙 | 근거 |
| --- | --- | --- |
| **R1** | **약관이 확정되기 전에는 검색하지 않는다** | 100권을 섞어놓고 닮은 것을 찾으면 아무거나 집어온다 |
| **R2** | **어느 약관으로 답하고 있는지 항상 표시한다** | 보이지 않으면 FA가 고객에게 옮길 수 없고, 틀려도 무엇이 틀렸는지 모른다 |
| **R3** | **스코프 밖 결과는 점수가 높아도 버린다** | 약관은 서로 90%가 닮아 남의 조항이 1등으로 올라온다 |
| **R4** | **검색이 못 하는 「모르겠다」를 우리가 만든다** | 100권이 다 닮아도 1등은 반드시 나온다. 「해당 조항 없음」을 명시적 상태로 둔다 |
| R5 | **면책이 먼저다.** 면책에 걸리면 지급사유가 있어도 뒤집지 못한다 | 지급사유를 먼저 보이면 FA가 그 줄에서 읽기를 멈춘다 |
| R6 | **판을 추측하지 않는다.** 시점이 특정되지 않으면 최신 판으로 답하지 않는다 | 개정 전 가입자에게 틀린 답을 주는 것이 답을 못 하는 것보다 나쁘다 |
| R7 | **약관의 담보 ≠ 가입한 담보** | 약관에는 가입 *가능한* 담보가 전부 들어 있다 |
| R8 | **1차에서 금액을 말하지 않는다** | 1.2 참조 |
| R9 | **면책 · 미가입에 0원을 쓰지 않는다.** 숫자가 아니라 사유를 둔다 | 0원은 계산 결과처럼 보이지만 지급 자체가 성립하지 않는 것이다 |
| R10 | **비용은 먼저 밝히고 동의를 받는다.** 단가 미확정 구간에서는 요청 의사만 받는다 | 금액을 모른 채 받는 동의는 백지 동의다 |
| R11 | **최종 판단자는 사람이다.** 확정은 보상 심사로 넘긴다 | 금융분야 AI 가이드라인의 **보조수단성** 원칙 |
| R12 | **근거의 종류를 화면에서 구분한다** — 약관 원문 / 보장 데이터(외부) / 일반지식 | 외부 데이터가 틀렸을 때 책임 범위를 가릴 수 있어야 한다 |
| R13 | **벤더에 개인정보를 보내지 않는다** | IA-SEC-001 |
| **R14** | **고객을 만들지 않아도 물을 수 있다** | 대부분은 한 건 확인하러 온다. 등록을 앞세우면 그 한 번이 사라진다 |
| **R15** | **고객 폴더는 그 고객 약관으로만 답한다** | 폴더가 곧 검색 범위다. 남의 계약 조항이 섞일 자리를 없앤다 |
| **R16** | **답할 수 있는 범위를 숫자로 밝힌다** | 계약 4건을 등록해도 약관이 2건뿐이면 「지금 답할 수 있는 건 2건」이라고 쓴다 |

## 6. 1차 상세 요구사항 — 기능

### IA-FUN-001

| 분류 | 기능 | 고유번호 | IA-FUN-001 | 단계 | 1차 | 담당 | |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 약관 스코프 확정 — 찾기 전에 정확한 상품을 짚어낸다

**정의** 질문에 답하기 전에 어느 약관 한 권을 볼 것인지 사용자가 직접 좁혀 확정하는 기능. **2.2의 1단계에 대응하며 이 시스템의 첫 관문이다**

**요구사항**

- **보험사 → 상품 → 가입 시점** 세 단계로 약관 1권을 확정할 수 있어야 함
- 스코프가 확정되지 않은 상태에서는 **약관 검색을 호출하지 않아야** 함
- 확정된 스코프를 화면에 **상시 표시**하고 언제든 변경할 수 있어야 함

**상세기술**

- **「AI가 되묻는다」가 아니라 「사용자가 미리 고른다」로 만든다.** 질문이 들어오는 순간 이미 1권으로 좁혀져 있으면 「찾기」 문제 자체가 사라진다. FA는 보험사와 상품을 이미 알고 있으므로 두세 번이면 끝나고 마찰이 거의 없다
- **보험사는 치거나 눌러서 고른다.** 이름을 알면 그대로 입력하고, 모르면 눌러 목록에서 고른다. 어느 쪽이든 **목록에 있는 값으로만 확정**한다 — 자유 입력만 받으면 「디비손보」 · 「DB손해」로 표기가 흔들려 같은 약관이 갈라진다
- **상품은 검색으로 매칭한다.** 상품명을 치면 후보가 나열되고 그중에서 고른다. 이름이 겹치는 상품(「참좋은동행」 · 「참좋은동행Ⅱ」 · 「참좋은운전자상해」)을 나란히 놓고, **판 개수를 함께 표시**해 다음 단계를 예고한다. 한 건만 자동 선택하지 않는다
- **진입점은 일반 답변 하단의 「약관 등록하기」 버튼이다.** 일반 답변을 먼저 내주고, 가입한 상품 기준으로 확인해야 할 때 FA가 눌러 들어온다. 「고객」을 앞세우지 않는다 — 등록부터 해야 하는 화면으로 읽힌다
- **보종(장기 · 자동차 · 일반 · 통합 · 퇴직연금)은 선택 단계로 두지 않는다.** 한 단계를 더 두면 FA가 「내 계약이 장기인가 통합인가」를 멈춰서 생각하게 되는데, 상품명은 이미 알고 있으므로 치는 편이 빠르다. 보종은 **검색 결과의 꼬리표와 목록 필터로만** 쓴다(IA-DAT-001)
- 스코프 단계와 상태

  | 단계 | 확정된 것 | 검색 가능 |
  | --- | --- | --- |
  | 0 | — | ❌ |
  | 1 | 보험사 | ❌ |
  | 2 | + 상품 | ❌ 판이 여럿이면 답이 달라진다 |
  | **3** | **+ 판(시행일)** | **✅ 여기서만 건다** |

- 검색은 **약어 · 별칭**도 받는다(「참좋은동행」 → 「무배당 프로미라이프 참좋은동행보험」). 다만 **확정은 목록에서** 한다
- **실손의료보험은 판이 아니라 「세대」로 고르게 한다.** 실손은 1~4세대 표준약관으로 갈리고 보상 판정의 큰 갈래도 세대가 정하므로, 판 목록을 150개 늘어놓는 대신 **1세대 / 2세대 / 3세대(착한실손) / 4세대**를 칩으로 준다. 세대 안에서 다시 갈릴 때만 시행일을 묻는다
- **실손은 갱신 · 전환으로 세대가 바뀐다.** 가입 시점만으로 세대를 정하면 전환한 계약에서 틀리므로, 실손일 때는 「가입 시점」이 아니라 **「지금 적용 중인 세대」**를 묻고, 모르면 증권 확인을 안내한다
- **선택을 건너뛰고 바로 묻는 경우** — 모든 상품 공통 조항으로 답할 수 있는 질문이면 그냥 답하고, 상품마다 다른 조항일 때만 선택을 요구한다(IA-FUN-002가 판별한다). 매번 선택을 강요하면 도구가 무거워진다
- 이미 확정된 스코프가 있으면(약관북에서 열고 들어옴, 세션에 있음) 다시 고르게 하지 않는다
- 스코프 미확정 상태로 검색이 호출되면 **예외로 실패시킨다.** 조용히 통과시키면 다른 상품 조항으로 답하고도 아무도 모른다
- **고객을 만들지 않아도 여기까지 온다.** 약관 스코프는 「누구의 계약인가」와 무관하게 보험사 · 상품 · 판만으로 정해지므로, 고객 등록을 앞세우지 않는다
- 확정 직후 두 갈래를 준다

  | 갈래 | 하는 일 | 언제 |
  | --- | --- | --- |
  | **「약관 선택 완료」** | 그대로 질문으로 간다. **고객 등록 없음** | 한 건만 확인하고 끝낼 때 — **기본값** |
  | 「고객 등록 후 이 약관 등록하기」 | 고객을 만들고 그 약관을 폴더에 쌓는다 | 이어서 상담할 고객일 때 |

  **앞쪽이 기본이고 뒤쪽이 선택이다.** 순서를 바꾸면 「한 건만 물어보려던」 FA가 등록 화면에서 이탈한다

**산출정보** 화면정의서, 스코프 단계 정의서, 선택기 컴포넌트 명세, 단위테스트 결과서

### IA-FUN-002

| 분류 | 기능 | 고유번호 | IA-FUN-002 | 단계 | 1차 | 담당 | |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 질문 분류 및 소스 라우팅

**정의** 질문을 유형별로 분류해 어느 소스를 쓸지, **약관 스코프 확정이 필요한지**를 결정하는 기능

**요구사항**

- 질문을 8개 유형(개념 / 판매 / 상품정보 / 담보용어 / **보상** / 인수심사 / 절차 / 계약가치)으로 분류하여야 함
- 유형별로 **스코프 필요 여부**와 사용할 소스를 결정하여야 함
- 분류는 LLM이 수행하되 **라우팅 판단은 규칙 코드로 고정**하여야 함

**상세기술**

- 라우팅 표는 코드 상수로 관리하며 LLM 출력에 좌우되지 않는다. LLM이 「약관이 필요 없다」고 해도 보상 유형이면 약관 경로로 간다
- **스코프 필요 여부를 여기서 가른다** — 이것이 「매번 선택을 요구하지 않는」 근거다

  | 질문 | 스코프 |
  | --- | --- |
  | 「골절진단비가 뭔가요?」 (약관 공통 정의) | 불필요 — 바로 답한다 |
  | 「음주운전 사고도 지급되나요?」 (상품 · 판마다 다름) | **필수** |
  | 「청구할 때 뭐 필요해요?」 (절차) | 불필요 |

- **담보 지목 범위**를 함께 판별한다
  - *지목형* — 「골절진단비 나오나요」처럼 담보가 명시된 질문 → 해당 담보만 조회
  - *열거형* — 「골절됐는데 보상되나요」처럼 상황만 있는 질문 → **걸릴 수 있는 담보를 모두 열거**한다. 좁게 잡으면 청구 누락이 생기므로 넓게 걸고 FA가 판단하게 한다
- 분류 실패 · 저확신 시 임의 라우팅하지 않고 스코프 확정 경로로 보낸다

**산출정보** 라우팅 정의서, 질문유형 분류 기준서, 분류 프롬프트 명세, 단위테스트 결과서

### IA-FUN-003

| 분류 | 기능 | 고유번호 | IA-FUN-003 | 단계 | 1차 | 담당 | |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 약관 시점 특정 및 되묻기 (보완 경로)

**정의** 선택기를 거치지 않고 바로 질문한 경우, 최소 횟수로 되물어 스코프를 확정하는 보완 경로

**요구사항**

- 보상 답변은 **계약 체결 시점에 시행 중이던 판**을 기준으로 하여야 함
- 스코프가 확정되지 않은 경우 보험사 → 상품 → 가입 시점 순으로 되물어야 함
- 이미 확정된 정보는 다시 묻지 않아야 함

**상세기술**

- **되묻기는 기본 경로가 아니라 보완 경로다.** 기본은 IA-FUN-001의 선택기다
- **되묻기는 걸러낸 뒤에만 한다.** ① 세션에 이미 있음 ② 고객 폴더에 해당 계약이 있음 ③ 판이 하나뿐임 — 셋 중 하나면 묻지 않는다
- **실손은 세대를 묻는다.** 「몇 년 가입」 대신 「1~4세대 중 어느 것인가」를 묻고, 모르면 가입 시점으로 추정하되 **전환 가능성을 함께 안내**한다
- **가입 시점은 「연 · 월」까지만 받는다.** 약관 시행일이 대개 매월 1일이고 개정이 분기 · 반기 시작일에 몰리므로 연 · 월만으로 판이 확정되는 경우가 대부분이다. 월 경계에 걸쳐 판이 2개 이상 남을 때만 일자를 추가로 묻는다
- **판 후보가 6개 이하일 때만 칩(버튼)으로 제시**한다. 한 상품에 판이 150개를 넘는 경우가 있어 전량 나열이 불가능하므로, 초과 시에는 연 · 월 입력만 받는다
- 상품 후보가 8개를 넘으면 나열하지 않고 **보험사부터** 좁힌 뒤 상품명 검색으로 넘긴다
- 상품명 정규화 시 배당 표기(무배당 등)만 걷어내고 **괄호 안 보장형태 · 납입방법 표기는 유지**한다. 「동행(사망보장형-월납)」과 「동행 Plus(월납)」은 약관 파일이 다르다
- 이름이 정확히 일치해도 후보를 단독 확정하지 않는다
- 되묻기 선택지에 **미등록 상품도 포함**하고 「약관 준비중」으로 표시한다. 목록에 아예 없으면 FA는 상품명을 잘못 말한 것인지 자료가 없는 것인지 구분하지 못한다
- **되묻는 횟수를 지표로 관리한다.** 선택기가 잘 동작하면 이 값이 낮아져야 정상이다

**산출정보** 되묻기 흐름도, 판 해석 규칙 정의서, 상품명 정규화 규칙서, 화면정의서

**요구사항**

- 합계는 `지급가능` 건만 합산하고, 제외된 건수와 사유를 함께 표시한다
- **막힌 건도 숨기지 않는다.** 면책 · 미가입 · 확인 필요 건을 목록에서 빼면 FA가 다시 확인해야 한다

### IA-FUN-005

| 분류 | 기능 | 고유번호 | IA-FUN-005 | 단계 | 1차 | 담당 | |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 고객 등록 및 상담 컨텍스트

**정의** FA가 담당 고객을 만들고, 현재 상담이 어느 고객 기준인지를 화면에 명시적으로 유지하는 기능. **상담의 전제 조건이 아니라, 자료를 쌓고 싶을 때 고르는 선택지다**

**요구사항**

- **고객을 만들지 않고도 질문 · 약관 확인 · 답변이 모두 되어야 함**(R14)
- 고객 생성의 **필수 입력값은 이름 하나**여야 함. 주민등록번호 · 연락처 · 생년월일은 수집하지 않아야 함
- 동일 이름의 담당 고객이 있으면 **생성 전에 제시**하여 중복 생성을 방지하여야 함
- 동명이인을 가를 수 있도록 **구분 메모(선택)** 를 입력받아야 하며, **여러 개를 붙일 수 있어야** 함
- 상담 화면에 현재 대상 고객을 항상 표시하여야 함

**상세기술**

- **구분 메모 입력란을 이름 아래에 함께 둔다.** 「선택 · 여러 개 붙일 수 있습니다」라고 라벨에 밝히고, 해시태그처럼 **＋ 버튼으로 계속 더하고 ✕로 뺀다** — 「92년생」 · 「강남지점」 · 「소개 · 김철수」. 지점 · 소개자 · 상담 맥락처럼 FA가 나중에 찾을 단서가 여럿이기 때문이다
- 메모는 목록 · 폴더 · 컨텍스트 바에서 이름과 함께 표시하고, **메모로 고객을 검색**할 수 있게 한다
- **메모에도 식별정보를 담지 않는다.** 입력란 아래에 「주민번호 · 연락처는 받지 않습니다」를 상시 표시한다 — 보험 서비스라 개인정보를 요구할 것으로 예상하는 FA에게 **안 받는다는 사실 자체가 안내**가 된다
- 고객 식별자는 이름과 분리해 발급한다(동명이인 · 개명 대응)
- 고객 목록 조회는 **언제나 담당 FA 단위로 한정**한다. 담당이 아닌 고객은 검색으로도 나오지 않고, 식별자를 직접 지정해도 조회되지 않는다
- **대부분의 상담은 한 건 확인하고 끝난다.** 「이 고객 진단금 되나요」 한 번 물어보려는 FA에게 고객 등록을 먼저 시키면 그 한 번이 사라진다. 등록은 **쌓고 싶을 때만** 나타난다
- 고객이 붙지 않은 상담도 그대로 동작한다 — 답변 · 근거 조항 · 면책 판정이 전부 나온다. 다만 **약관북 · 보장맵에 남지 않으므로** 답변 아래에 「이 고객 건으로 저장」을 조용히 놓아둔다(강요하지 않는다)
- 상담 중 「이 고객 기준으로 확인하기」를 눌렀을 때 고객이 없으면 **그 자리에서** 생성 화면을 띄운다. 다른 메뉴로 이동시키면 흐름이 끊긴다
- 상담이 끝나면 세션 컨텍스트를 내린다

**산출정보** 화면정의서, 고객 데이터 항목 정의서(최소화 근거 포함), 권한 매트릭스

### IA-FUN-006

| 분류 | 기능 | 고유번호 | IA-FUN-006 | 단계 | 1차 | 담당 | |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 약관 등록 — 다중 경로

**정의** 고객의 가입 계약을 보장맵에 등록하는 기능. 상황에 따라 빠른 경로를 우선 제시한다

**요구사항**

- 등록 경로를 **빠른 순으로 정렬**하여 제시하고, 아직 열리지 않은 경로(My Data)는 **표시하되 선택 불가**로 두어야 함
- 현재 상황에서 사용할 수 없는 경로는 목록에서 제외하여야 함
- 등록 후 **다른 상품 추가 등록**을 이어서 유도하여야 함

**상세기술**

- 보험사 → 상품 검색 → 등록만 제공하면 한 건에 3단계이고, 고객 한 명이 계약을 대여섯 건 보유하므로 **15단계**가 된다. FA는 한 번 해보고 다시 하지 않는다

  | 순 | 경로 | 특징 |
  | --- | --- | --- |
  | 1 | **My Data 가져오기** | **가장 빠름 · 추후 오픈.** 고객 계약이 한 번에 들어온다. 개인인증 · 동의 범위 확인 후 열린다 |
  | 2 | **대화에서 말한 상품 등록** | 이미 말한 상품을 다시 검색하게 하지 않는다. **현재 최선** |
  | 3 | 보험사 · 상품명 검색 | My Data가 열리기 전까지 기본 경로 |

- **안 열린 경로도 화면에 두되 잠근다.** 곧 열릴 경로가 있다는 사실 자체가 안내이고, FA가 「왜 하나씩 넣어야 하나」를 납득하는 근거가 된다. 「현 시점 오픈하지 않음」으로 표시하고 고를 수 없게 한다
- **「최근 등록한 상품에서 고르기」는 두지 않는다.** 그 목록은 결국 다른 고객에게 등록했던 상품이라, 지금 상담 중인 고객과 무관한 계약을 화면에 끌어온다. 상품명을 아는 상태라면 검색이 더 빠르고 오해도 없다. 최근 등록 이력은 운영 지표(초기 등록 목록 산정)로만 쓴다
- 1차에는 대량 등록 경로가 없으므로 보장맵은 **상담하면서 하나씩** 쌓인다. 등록 한 건의 단계 수를 줄이는 것이 그만큼 더 중요하다
- 업로드 결과는 **저장 전에 확인 화면**으로 보여준다. 잘못 읽힌 계약이 확인 없이 보장맵에 남으면 안 된다
- 전체 선택 상태로 시작하되 개별 해제가 가능해야 한다(해지 계약 · 무관한 계약 제외)
- **「계약을 확인한 것」과 「약관이 등록된 것」을 목록에서 구분 표시**한다. 이 구분을 숨기면 보장맵은 채워진 것처럼 보이는데 정작 답을 못 한다
- 요약 문구에 **등록되는 계약 수와 지금 답할 수 있는 수를 나눠** 쓴다 — 「계약 4건 등록 · **지금 답할 수 있는 건 약관 2건**」. 「계약 4건」만 쓰면 4건 다 물어볼 수 있는 줄 알고, 나머지를 물었다가 「없다」를 받는 순간 도구를 불신한다(R16)
- 등록과 동시에 **확보 요청도 함께 접수**할 수 있게 한다. 두 번 오게 하지 않는다

**산출정보** 화면정의서, 리포트 파서 명세서, 업로드 파일 형식 · 검증 규칙서, 사용자 매뉴얼

### IA-FUN-008

| 분류 | 기능 | 고유번호 | IA-FUN-008 | 단계 | 1차 | 담당 | |
| --- | --- | --- | --- | --- | --- | --- | --- |

**명칭** 약관북 — 고객별 폴더

**정의** 상담 중 확인한 약관을 고객별 폴더로 누적하고, 다음 상담에서 스코프 선택 없이 바로 열 수 있게 하는 기능

**요구사항**

- 답변에 사용한 약관을 **고객 건으로 지정해 누적**할 수 있어야 함
- 약관북은 상담과 **나란한 최상위 메뉴**여야 하며, 첫 화면은 질문창이어야 함
- 폴더에서 약관을 열면 **스코프가 곧바로 확정**되어야 함
- 폴더를 열고 질문하면 **그 고객의 확보된 약관 집합 안에서만** 답하여야 함(R15)

**상세기술**

- 폴더에서 여는 것이 **스코프 확정의 가장 빠른 경로**다. 클릭 한 번으로 IA-FUN-001의 세 단계가 끝난다
- **폴더 스코프는 「한 권」이 아니라 「한 고객의 책장」이다.** 그 고객이 등록한 약관 집합이 곧 검색 범위이며, 집합 밖 조항은 점수가 높아도 쓰지 않는다. 담보가 여러 계약에 걸치면 **걸리는 계약을 모두** 제시해 청구 누락을 잡는다 — 폴더 질문의 가장 큰 효용이다
- **판이 미확정인 계약은 검색에서 빼되 「미확정 N건 제외」로 밝힌다.** 조용히 빼면 그 계약이 확인되지 않았다는 사실이 사라진다
- 컨텍스트 바에 **확보된 건수 기준**으로 표시한다 — 「차승희 · 약관 4건 · 확보된 4건 안에서만 답합니다」
- 「최근 상담」(대화 이력)과 약관북(고객별 약관)은 성격이 다르므로 같은 목록에 섞지 않는다
- 폴더 정렬은 **약관이 최근에 추가된 순**
- 검색은 **고객명과 상품명 양쪽**으로 되어야 한다
- 같은 고객 · 같은 약관은 중복 저장하지 않는다
- 연결 출처(상담 중 저장 / 보장분석 / 유료 확보)를 보관해 **비용을 들여 확보한 약관이 몇 명에게 쓰이는지** 집계할 수 있게 한다
- 상담 제목에 상품 · 판을 남긴다(예: 「차승희 · 골절 진단금 / 내맘같은어린이보험 2019.04 판」)

**산출정보** 화면정의서, 데이터 모델 정의서, 검색 사양서

### IA-FUN-009

**명칭** 미등록 약관 확보 요청 및 비용 동의

**정의** 벤더에 색인되지 않은 약관을 FA가 확보 요청하고 비용 부담에 동의하는 절차

**요구사항**

- 미등록 약관이어도 **상품과 가입 시점을 먼저 확정한 뒤** 요청을 접수하여야 함
- 비용이 발생할 수 있음을 **접수 전에** 고지하고 동의를 받아야 함
- 동일 상품 · 동일 판에 대한 선행 요청이 진행 중이면 **중복 과금하지 않아야** 함

**상세기술**

- **단가 미확정 구간의 처리(현재 상태)** — 금액을 표시하지 않고 **요청 의사만** 받는다

  > 「…확보에는 등록 비용이 발생할 수 있습니다. 요청을 남기시면 비용과 진행 여부를 확인해 안내드리겠습니다.」 `[확보 요청하기]` `[취소]`

  접수된 요청은 *청구 대상 후보*이지 결제 동의가 아니다. 실제 청구는 금액을 안내하고 **다시 동의를 받은 뒤에만** 한다
- 고지 화면에 ① 무엇에 대한 비용인지(상품명 + 판/시행일까지) ② 금액 ③ **취소**를 항상 함께 둔다
- 미등록이어도 스코프 확정을 끝까지 하는 이유는 등록 단위가 「상품」이 아니라 **「상품 + 판」**이기 때문이다
- 요청은 세 갈래로 처리한다

  | 상황 | 처리 |
  | --- | --- |
  | 색인에 있음 | 스코프 확정 후 검색 · 답변 |
  | 마스터에 있으나 미색인 | 시점 확인 → 없다고 안내 + 요청 기록(상품 ID 포함) |
  | 마스터에도 없는 이름 | 시점 확인 → 없다고 안내 + 요청 기록(이름만) |

  세 번째를 「모르는 상품입니다」로 끝내지 않는다. 그렇게 하면 우리가 모르는 상품일수록 요청이 쌓이지 않아 정작 필요한 약관이 등록 목록에 영영 오르지 않는다
- **요청 시점의 원 질문을 함께 저장**한다. 검수와 알림에 그대로 쓴다
- 「확보 대상으로 등록했습니다」처럼 **등록을 약속하지 않는다.** 「접수했고 검토 후 안내」까지만 말한다

**산출정보** 화면정의서, 비용 고지 문안, 요청 상태 전이 정의서, 과금 정책서(정책 확정 후)

**명칭** 확보 파이프라인 · 검수 · 알림

**정의** 접수된 요청을 약관 확보 → 색인 → 검수 → 알림까지 처리하는 운영 흐름

**요구사항**

- 상태를 `접수 → 대기 → 확보 → 색인 → 검수 → 알림`으로 관리하고 각 단계 전이를 기록하여야 함
- **검수를 통과한 뒤에만** 완료 알림을 발송하여야 함
- 확보 실패 시에도 사유와 함께 종료를 알려야 함

**상세기술**

- **임베딩이 끝난 것과 답할 수 있는 것은 다르다.** 파일 파싱 오류, 특약 미구분, 판 오매핑이 있으면 등록은 됐는데 답이 안 나온다. 이 상태에서 「등록됐습니다」를 알리면 FA가 다시 물어보고 또 실패한다 — 신뢰가 한 번에 깨진다
- 검수 기준을 「임베딩 성공」이 아니라 **「그 FA의 원 질문에 근거 조항이 나오는가」**로 둔다
- 검수 통과 조건에 두 가지를 포함한다
  - **면책 조항이 함께 검색되는가** — 지급사유는 잘 찾는데 면책을 놓치는 색인은 가장 나쁜 형태로 틀린다
  - **스코프 밖 조항이 섞여 오지 않는가** — 다른 상품 조항이 반환되면 색인 메타데이터나 필터가 동작하지 않는다는 뜻이다
- 알림 규칙
  - **원 질문을 알림에 함께 싣고** 탭 한 번으로 그 맥락으로 돌아가게 한다
  - 같은 FA · 같은 약관은 여러 번 물었어도 **1회만** 알린다
  - 배치에서 여러 약관이 동시에 등록되면 **FA별로 묶어 한 건**으로 보낸다
  - **접수 즉시** 「접수했습니다」를 보여준다
- 배치 주기는 **주 1회 고정**. 주기가 일정해야 예상 시점을 안내할 수 있다

**산출정보** 업무흐름도, 상태 전이 정의서, 검수 체크리스트, 알림 템플릿 목록, 배치 운영 절차서

**요구사항**

- 답변 화면에 **현재 스코프(보험사 · 상품 · 판)를 상시 표시**하여야 함

- 스코프 표시는 답변에 붙는 각주가 아니라 **화면에 고정된 바(bar)**다. 스크롤해도 보이고 거기서 바로 바꿀 수 있어야 한다

  > 📄 **DB손해보험 · 무배당 프로미라이프 참좋은동행보험 · 2021.09 시행 약관** 〔약관 변경〕

  이것이 없으면 FA는 답을 고객에게 옮길 수 없고, 틀렸을 때 **무엇이 틀렸는지도 알 수 없다**
- 표시 구조: **스코프 바 → 판정 → 담보별 결과 → 근거 조항(면책 우선) → 근거 종류 → 유의 문구**
- 근거 종류 표기

  | 종류 | 표기 | 책임 |
  | --- | --- | --- |
  | 약관 원문 | 「제5조 제2항」 + 원문 | 확정된 약관 |

  | 일반지식 | 「Micky DATA — 보험 일반지식」 | 특정 상품 확정이 아님 |

  섞어 쓰면 외부 데이터가 틀렸을 때 어디까지가 우리 책임인지 가릴 수 없다(R12)
- 조항 원문은 길므로 요약을 먼저 보이고 **펼쳐보기**로 원문을 제공한다. 다만 FA는 고객에게 근거로 제시해야 하므로 원문 인용을 요약으로 대체하지 않는다
- 답변 하단에 **기준일**(약관 시행일 · 자료 기준일)을 표시한다
- 톤은 실무형으로 한다. 단정하는 대신 확인이 필요한 쟁점을 짚고 최종 판단은 보상 심사로 넘긴다(R11)

**명칭** 스코프 강제 및 검색 결과 제한

**정의** 확정된 약관 한 권 밖으로 검색이 새어 나가지 않도록 막는 통제. **2.2의 2단계에 대응하며 정확도의 마지막 방어선이다**

**요구사항**

- 스코프가 확정되지 않은 상태의 검색 호출은 **실패시켜야** 함
- 반환된 결과 중 **스코프 밖 조항은 점수와 무관하게 제외**하여야 함
- 유사도 하한 미만의 결과는 근거로 쓰지 않아야 함
- 남는 근거가 없으면 **「해당 조항 없음」으로 종료**하여야 함

**상세기술**

- **벤더 필터를 신뢰하고 넘기지 않고 받은 쪽에서 한 번 더 건다.** 필터가 없거나 헐거우면 다른 상품 조항이 그대로 답변에 실리는데, 약관은 서로 90%가 닮아 **그 사실이 눈에 띄지도 않는다**
- 판별 키는 `(보험사, 상품, 판)`이다. 셋 중 하나라도 다르면 버린다
- 스코프는 두 가지다 — **단일 약관**(선택기로 확정한 한 권)과 **고객 집합**(폴더를 열어 잠긴 그 고객의 약관들). 규칙은 같다: 집합 밖은 버리고, 남는 것이 없으면 「해당 조항 없음」으로 끝낸다
- **순위를 낮춰가며 채우지 않는다.** 결과가 비면 비는 것이 정답이다. 「그나마 닮은 것」을 조항으로 제시하면 R4가 무너진다
- **버린 것을 로그에 남긴다** — 채택 / 스코프밖 / 점수미달 건수. 스코프 밖 반환이 계속 나오면 벤더 색인이나 필터가 동작하지 않는다는 신호이고, 이 값이 IA-FUN-010 검수의 근거가 된다
- 유사도 하한은 설정값으로 두고 골든셋(IA-TST-001)으로 조정한다. 너무 높으면 답할 수 있는 것도 못 하고, 너무 낮으면 「닮은 것 중 1등」이 근거로 올라온다

- 답변 하단에 분기를 둔다 — `[약관 등록하기]` / `[이 답변으로 충분해요]`. **두 선택지를 같은 무게로** 둔다. 일반 답변은 실패가 아니다. 안내 문구는 「가입한 상품을 선택하면 해당 상품의 약관 기준으로 답합니다」
- 이 버튼은 **약관을 고르는 입구이지 고객을 만드는 입구가 아니다.** 고객 없이 약관만 골라 답을 받고 끝낼 수 있다(R14)
- **앞 버튼이 IA-FUN-001 스코프 선택기의 입구다.** 여기서 보험사 → 상품 검색 → 판으로 이어진다
- 이미 스코프가 확정된 상담에서는 분기를 띄우지 않는다
- 자료 유효기간 · 태그 체계는 AX팀 공유 예정(TBD). 인덱스 단계에서 만료 자료를 거르는 구조를 먼저 만들어 둔다

**요구사항**

- 정규화 규칙 — 배당 표기(무배당 등) · 공백 · 특수문자는 정리하되 **괄호 안 보장형태 · 납입방법 · 판 표기는 유지**한다. 약관 파일이 그 단위로 갈린다

- 판 확정 로직은 계약년월 → 시행 중이던 판으로 해석한다
- **실손은 판 위에 「세대」 축을 하나 더 둔다.** 1세대(~2009.09) · 2세대(2009.10~2017.03) · 3세대 착한실손(2017.04~2021.06) · 4세대(2021.07~)로 판을 묶어, 선택기와 되묻기가 세대 단위로 동작하게 한다. **계약년월 → 세대는 추정이며, 전환 이력이 있으면 어긋난다**

```
고객 데이터  ──  우리 서버에만 머문다
      │
      │  스코프(보험사 · 상품 · 판) + 담보명만 추출
      ▼
  검색 질의  ──────  외부 API (누구 것인지 모른다)
      │
      │  조항 원문 반환
      ▼
  답변 조립  ──────  우리 서버에서 계약 정보와 결합
```

- 이 분리를 **코드로 강제**한다

**명칭** My Data · 보장분석 연동 및 담보 ↔ 조항 매핑

**정의** 보장분석 데이터를 구조화해 적재하고, 외부 담보코드와 우리 약관 조항을 잇는 매핑을 관리하는 기능

- **외부 데이터 의존을 명시한다.** 업체 데이터가 틀리면 우리 답도 틀린다. 그래서 답변에서 **담보 데이터로 답한 부분과 약관 원문으로 답한 부분을 구분해 표시**하고(R12), 책임 범위를 계약서에 명시한다
- 개인정보 흐름(연동 → 업체 → 우리)의 3자 제공 · 위수탁 동의 범위를 확인한다
- 등록 목록 산출은 (보험사 + 상품 + 계약년월 + 건수) 형태로만 집계한다. 이 집계값은 개인정보가 아니다
- **비용 관점의 근거** — 과금이 파일 단위이므로 상품 단위 구매는 `보장형태 × 납입방법 × 판` 배수만큼 낭비가 곱해진다. 반면 리포트가 지목한 계약은 조합이 이미 하나로 정해져 **계약당 필요한 파일이 정확히 1건**이다

  | --- | --- | --- |
  | 1건 | 120개(전체) | 100% |
  | 3건 | 66개 | 77.6% |
  | 6건 | 33개 | **26.3%** |

| 3 | **약관 파일 1건당 단가와 과금 단위** | 판당 / 용량 / 구간 정액 중 무엇인지에 따라 등록 전략이 전부 달라진다 |
| 4 | **상품당 약관 파일 수(배수)** | 「동행」 하나의 실제 약관 목록만 받아도 배수가 나온다. 배수 6이면 200파일에 손보 상품이 4개만 들어간다 |
| 5 | **판도 파일 수에 곱해지는가** | 곱해지면 개정이 잦은 상품은 전량 등록이 불가능하다. 실손은 1~4세대로 정리되므로 예외 |
| 6 | 근거 청크 반환 여부 | 반환 안 되면 근거 조항을 제시할 수 없다 |
| 7 | 유사도 점수 반환 여부 | 하한을 걸 수 없다 |
| 8 | 프롬프트 · 답변 형식 제어 가능 여부 | 면책 우선 표시를 강제할 수 있는지 |
| 9 | retrieval-only 모드 유무 | 있으면 우리가 직접 생성하는 선택지가 열린다 |
| 10 | 청크 메타데이터 실측 (IA-DAT-002 표) | **상품 · 판 식별자와 특약 구분이 핵심** |
| 11 | 색인 커버리지 · 갱신 주기 | 초기 등록 목록 산정 |
| 12 | 멀티턴 지원, 모델 목록 · 비용 · 지연, 인증 · 호출 한도 | 설계 · 성능 산정 |

### 10.2 내부에서 확정해야 할 값

| 항목 | 필요한 것 | 미확정 시 |
| --- | --- | --- |
| **보종 분류 기준** | 상품에 붙일 보종을 무엇으로 매길지 | 검색 결과 꼬리표 · 필터가 비게 된다 (선택 단계는 아니므로 오픈은 가능) |
| **초기 등록 목록** | 첫 시작은 **현재 판매 중인 약관 200개**. 그 구성에 무엇을 넣을지 | 실적 목록으로만 채우면 **영업용 약관을 사고 보상 질문은 못 덮는다** |
| **1차 오픈 종목** | 운전자보험 단독 권장 — 실적 상위 10개 중 7개, 담보 표준화, 판이 적다. **실손을 함께 열지 검토** — 세대 4개로 정리돼 파일 수 대비 효율이 가장 좋고 보상 문의도 많다 | 전 종목을 얕게 열면 품질 검증이 불가능하다 |
| **실손 세대 매핑** | 계약년월 → 세대 매핑표와, 전환 이력을 어떻게 확인할지 | 전환한 계약에 이전 세대 약관으로 답하게 된다 |
| **선구매 부담 분담** | 먼저 요청한 FA가 뒤따르는 FA 몫까지 부담하는 구조를 둘지 | 자주 쓰이는 약관일수록 처음 요청자만 돈을 낸다 |
| **환불 조건** | 확보 실패 외에 검수 미통과도 환불 대상인지 | 요청자 책임이 아닌 실패에 과금된다 |
| **FA 1인당 월 요청 한도** | 둘지 말지 | 소수 FA가 예산을 크게 소진할 수 있다 |
| **파일 원본 보관** | 업로드한 리포트 원본을 남길지 · 얼마나 | 보관 책임이 정의되지 않는다 |
| **알림 채널** | 사내 메신저 / 알림톡 / 이메일 / 인앱 | IA-INT-005 산정 불가 |
| **FA 규모 · 피크 동시접속** | 인원과 사용 패턴 | 성능 목표 산정 불가 |

### 10.3 법무 · 계약 검토가 필요한 것 — 설계로 해결되지 않는다

1. **동의 범위** — 고객이 보장분석에 동의할 때의 이용 목적에 「AI 상담 지원」이 포함되는가
2. **개인정보 흐름** — 연동 → 업체 → 우리. 3자 제공 · 위수탁 동의 범위 (2차)
3. **외부 데이터 책임 소재** — 업체 데이터가 틀려 우리 답이 틀렸을 때의 책임 범위를 계약서에 명시 (2차)
4. **보관 기간** — 데이터를 얼마나 보유할 것인가
5. **외부 전송 값의 성격** — 개인정보가 아니라는 판단의 확인. IA-SEC-001의 전송 항목 표가 근거 자료다
6. **고객 열람 · 삭제 요구** — 세션 · 저장소 · 로그에서 어떻게 지울 것인가
7. **고영향 AI 해당 여부** — AI 기본법상 해당하는지, 해당 시 이행 사항

> **동의 범위가 확인되기 전에도 1차는 진행할 수 있다.** 1차 범위에 보장분석 연동이 없고,
> 리포트는 FA가 직접 올리는 파일이며, 저장 없이 **세션에서만 쓰는 방식**을 선택할 수 있다.

## 11. 오픈 판정 — 무엇이 되면 여는가

7주 안에 전부 완성되지 않을 수 있다. **무엇이 안 되면 열지 않는지**를 먼저 정한다.

### 열지 못하는 조건 (하나라도 걸리면 연기)

- **확정된 약관 밖의 조항을 인용한 답변이 1건이라도** 나온다
- **스코프가 확정되지 않은 채 보상 답변이** 나간다
- 골든셋에서 **면책 조항을 놓치는 답변이 1건이라도** 나온다
- 스코프 안에 조항이 없는데 **「해당 조항 없음」 대신 그럴듯한 답을** 만든다
- 다른 판 · 다른 특약의 조항을 근거로 답한다
- **답변 화면에 어느 약관으로 답했는지 표시되지 않는다**
- **고객을 만들지 않으면 질문을 못 하는** 구간이 있다
- **고객 폴더에서 물었는데 그 고객 약관 밖의 조항이** 인용된다
- **등록 계약 수를 답변 가능 수처럼 표시**한다
- 담당하지 않는 고객의 자료가 조회된다
- 외부 API 전송 값에 개인 식별정보가 포함된다

### 없어도 여는 것 (2차로 넘김)

- 계약 연동 자동 확정 — 계단식 선택으로 시작
- 관리자 승인 화면 — 운영자 수기 처리로 대체
- 보장분석 API 연동 — 파일 업로드만으로 시작
- 금액 답변(초개인화) — 애초에 1차 범위 밖
- 약관 개정 알림 — 분기 점검으로 대체
- 외부 알림 채널 — 인앱 알림만으로 시작

### 축소해서 여는 것

- **종목을 운전자보험으로 좁혀 연다.** 전 종목을 얕게 여는 것보다, 한 종목에서 「FA가 고객에게 그대로 읽어줄 수 있는 수준」을 만드는 편이 낫다
- 확보 요청은 **요청 의사만 받는 형태**로 연다(단가 확정 전)
