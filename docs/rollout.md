# 약관 등록 전략 (100건으로 시작해서 넓히기)

약관을 처음부터 전부 등록하지 않는다. **우선 100건 규모로 벤더에 등록하고,
없는 약관은 역질문으로 받아서 채워나간다.**

이 방식의 요점은 등록 목록을 추측으로 정하지 않는다는 것이다.
FA가 실제로 물어본 약관이 다음 등록 대상이 된다.

## 비용 구조

| 구분 | 부담 | 선정 방식 |
| --- | --- | --- |
| **초기 등록 200개 상품** | 회사 | 실적 · 지정 목록 기준 (`registration_plan`) |
| 그 밖의 약관 | **요청한 FA** | 요청 시 비용 고지 → 동의 → 접수 |

초기 200개는 회사가 한 번에 등록하고, 그 밖의 약관은 필요한 FA가 요청하며 비용을 부담한다.
따라서 **접수 전에 금액을 고지하고 동의를 받는 단계가 반드시 들어간다**
(`NextAction.CONFIRM_PAID_REQUEST`). 동의 없이 비용이 발생하는 흐름은 만들지 않는다.

고지 화면에는 세 가지가 함께 나온다.

- **무엇에 대한 비용인지** — 상품명과 판(시행일)까지. 판이 정해져야 금액이 정해진다.
- **금액**
- **취소** — 항상 남긴다.

### 단가 미확정 — 현재 상태

벤더 등록 단가가 아직 정해지지 않았다. 이 상태에서 금액 없이
「비용이 발생합니다. 요청하시겠어요?」로 동의를 받으면 **백지 동의**가 된다.
FA가 얼마인지 모른 채 비용 발생에 동의하는 셈이라 그대로 두면 안 된다.

그래서 단가가 확정될 때까지는 **요청 의사만 받는다.**

> 「…확보에는 등록 비용이 발생할 수 있습니다.
> 요청을 남기시면 비용과 진행 여부를 확인해 안내드리겠습니다.」
> `[확보 요청하기]` `[취소]`

- 금액란은 「확인 후 안내」로 두고 숫자를 표시하지 않는다.
- 접수된 요청은 `billable=True, price=None` — **청구 대상 후보**이지 결제 동의가 아니다.
- 실제 청구는 금액을 안내하고 다시 동의를 받은 뒤에만 한다.

단가가 정해지면 `TermsPricing(price_per_edition=...)`을 주입하는 것만으로
「요청하기 (30,000원)」 형태의 확정 동의 흐름으로 바뀐다. 코드 변경은 필요 없다.

### 같은 약관을 두 번 사지 않는다

등록된 약관은 **전사가 함께 쓴다.** 따라서 같은 상품 · 같은 판을 다른 FA가 이미
요청해 진행 중이면 두 번째 FA에게는 비용을 받지 않고 대기 안내만 한다
(`RequestLog.pending_keys()`).

다만 이 규칙은 **먼저 요청한 FA가 뒤따르는 FA의 몫까지 부담하는 구조**를 만든다.
자주 쓰이는 약관일수록 처음 요청한 사람만 돈을 낸다.
분담 방식은 정책 결정이 필요하다(아래 「정해야 할 것」).

### 확보 실패 시 환불

약관 자체가 없거나(상품명 오인, 공시 미존재) 확보가 불가능한 경우
비용을 청구하지 않는다. 이미 결제됐다면 환불하고, 사유와 함께 알린다.
무응답이 가장 나쁘다.

## 회사 부담분(초기 200개)의 선정

벤더에 약관을 등록할 때 **비용이 발생한다.** 이 전제가 아래 모든 규칙을 정한다.

1. **초기 200개를 무엇으로 채우는지가 서비스 품질을 좌우한다.** 여기 들어간 상품은
   FA가 무료로 즉시 답을 받고, 빠진 상품은 매번 누군가 비용을 부담해야 한다.
2. **우선순위는 계약 건수 실적이다.** 보상 질문은 계약이 있는 곳에서 나온다
   (`docs/seed-products.md`).
3. **비용 단위는 판(edition)이다.** 같은 상품이라도 판마다 따로 등록해야 한다.
   실손처럼 판이 150개를 넘는 상품은 전체 등록이 비현실적이며,
   요청이 몰린 판만 골라 넣는다.
4. 회사 부담 예산을 추가로 집행할 때는 쌓인 요청을 근거로 삼는다.
   요청자가 여럿인 약관을 회사가 사 두면 개별 FA의 부담이 사라진다.

## 흐름

```
보상 질문
   │
   ├─ 약관 등록됨   → 상품 · 가입 시점 확정 → 검색 → 근거 조항과 함께 답변
   │
   └─ 약관 미등록   → 상품 · 가입 시점 확정 → 「없다」고 안내 + 확보 요청 접수
                                                        │
                                          요청 누적 → 등록 후보로 묶기
                                                        │
                                    수요 · 예산 기준 승인 ──┬── 승인 → 등록 → 검수 → 알림
                                                        │
                                                        └── 보류/미승인 → 사유 알림
```

승인 규칙(`select_within_budget`)

- 요청자가 **2명 미만이면 승인하지 않는다.** 한 사람이 열 번 물어도 단독 요청이면
  비용을 들일 근거가 약하다. 다음 배치에서 다시 평가한다.
- **상품 마스터에서 식별되지 않은 이름은 자동 승인 대상이 아니다.**
  오타일 수 있으므로 비용 집행 전에 사람이 본다.
- 남은 후보를 수요 순으로 예산(판 수)만큼 담는다.

수요 점수는 **요청한 FA 수를 요청 건수보다 무겁게** 본다.
한 사람이 열 번 물어본 것보다 열 사람이 한 번씩 물어본 쪽이
조직 전체로 더 자주 막히고 있다는 뜻이기 때문이다.

## 미등록이어도 역질문을 끝까지 하는 이유

없는 약관이면 바로 「없습니다」로 끝내는 편이 빠르다. 그런데도 상품명과
가입 시점을 먼저 묻는 이유는, **등록 요청이 「상품」이 아니라 「상품 + 판」
단위여야 하기 때문**이다.

상품명만 알면 어느 판을 등록해야 하는지 정해지지 않는다.
개정 이력이 있는 상품은 판이 여럿이고, 그중 FA에게 필요한 것은 그 계약의 판 하나다.
가입 시점을 받아야 등록 대상이 하나로 좁혀진다.

역질문이 두 가지 일을 겸하는 셈이다.

1. 등록된 약관이면 → 정확한 판으로 검색
2. 미등록 약관이면 → 정확한 등록 대상 수집

FA 입장에서 두 경우의 대화가 같으므로, 이 상품이 등록됐는지 몰라도 된다.

## 세 갈래 처리

| 상황 | 처리 |
| --- | --- |
| 벤더 인덱스에 약관 있음 | 판 특정 후 검색 · 답변 |
| 마스터에는 있으나 약관 미등록 | 시점 확인 → 없다고 안내 + 요청 기록 (상품 ID 포함) |
| 마스터에도 없는 이름 | 시점 확인 → 없다고 안내 + 요청 기록 (이름만) |

세 번째를 「모르는 상품입니다」로 끝내지 않는 것이 중요하다.
그렇게 하면 우리가 모르는 상품일수록 요청이 쌓이지 않아,
정작 필요한 약관이 등록 목록에 영영 오르지 않는다.
오타로 들어온 이름은 요청 건수가 낮아 우선순위에서 자연히 밀린다.

## 우선순위 집계

`RequestLog.candidates()`가 요청을 등록 후보로 묶고,
`select_within_budget()`이 예산 안에서 승인 대상을 고른다.

- 묶는 단위는 **보험사 + 상품 + 가입 연도**이며, 이것이 곧 비용 단위다.
  판 하나를 등록하면 그 판을 기다린 요청이 함께 풀린다.
- 같은 상품이라도 가입 연도가 다르면 다른 판이므로 비용도 따로 든다.
- 후보에 원 질문이 함께 실리므로, 등록 후 검수에 그대로 쓴다.

`RequestLog.priorities()`는 단순 빈도순 목록으로, 현황 파악용으로 남겨둔다.
실제 승인 판단은 `select_within_budget()`을 쓴다.

## 초기 100건을 무엇으로 채울까

초기 목록은 요청 데이터가 없는 상태에서 정해야 한다. 다음 순으로 보는 것이 안전하다.

1. **보유 계약이 많은 상품** — 보상 질문은 이미 가입한 계약에서 나온다
2. **보상 문의가 잦은 상품군** — 실손 · 암 · 운전자 등
3. **개정 이력이 많은 상품** — 판을 헷갈리기 쉬워 FA가 확인을 더 필요로 한다

1번은 계약 데이터(Cloud DATA)를 보면 바로 나오지만 이번 범위 밖이므로,
영업·보상 쪽에서 목록을 받아 정하는 편이 빠르다.

## 운영에서 볼 지표

- **미등록 비율** — 보상 질문 중 「약관 없음」으로 끝난 비율.
  이 값이 등록 확대(=예산 증액)의 근거가 된다.
- **등록 1건당 해소 요청 수** — 비용 효율. 이 값이 낮아지면 등록의 한계효용이
  떨어진 것이므로 예산을 줄이거나 기준을 올린다.
- **보류 누적** — 승인되지 않고 쌓인 후보. 늘어나기만 하면 예산이 부족한 것이다.
- **역질문 이탈** — 되물었는데 FA가 답하지 않고 나간 비율.
  높으면 되묻기가 과하거나 선택지가 잘못됐다는 신호다.

## 정해야 할 것

- **선구매 부담 분담** — 먼저 요청한 FA가 뒤따르는 FA 몫까지 부담하는 구조를
  그대로 둘지, 나중 요청자에게도 일부를 받을지, 아니면 요청이 N명 모이면
  회사가 사는 방식으로 갈지.
- **환불 조건** — 확보 실패 외에, 등록됐으나 검수를 통과하지 못한 경우(파싱 오류 등)도
  요청자 책임이 아니므로 환불 대상으로 볼 것인지.
- **한도** — FA 1인당 월 요청 한도를 둘지. 없으면 소수 FA가 비용을 크게 쓸 수 있다.

## 비용을 줄이는 방법

등록 비용이 제약이므로, 같은 예산으로 더 많이 답하려면 아래를 함께 본다.

- **판 정밀도 낮추기** — 개정 사이에 조항이 실제로 바뀌지 않은 판이 많다면,
  전 판을 다 넣지 않고 변경이 있었던 판만 넣는 방식을 벤더와 협의한다.
- **요청 몰림 활용** — 실손은 전 판이 아니라 요청이 몰린 연도 판부터 넣는다.
- **단가 확인** — 등록 단가가 판당인지, 파일 용량 기준인지, 정액 구간인지에 따라
  최적 전략이 달라진다. 이 문서의 계산은 **판당 균일 단가**를 가정한다.
