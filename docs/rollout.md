# 약관 등록 전략 (100건으로 시작해서 넓히기)

약관을 처음부터 전부 등록하지 않는다. **우선 100건 규모로 벤더에 등록하고,
없는 약관은 역질문으로 받아서 채워나간다.**

이 방식의 요점은 등록 목록을 추측으로 정하지 않는다는 것이다.
FA가 실제로 물어본 약관이 다음 등록 대상이 된다.

## 흐름

```
보상 질문
   │
   ├─ 약관 등록됨   → 상품 · 가입 시점 확정 → 검색 → 근거 조항과 함께 답변
   │
   └─ 약관 미등록   → 상품 · 가입 시점 확정 → 「없다」고 안내 + 등록 요청 기록
                                                        │
                                            요청 누적 → 빈도순 우선순위
                                                        │
                                                  다음 등록 배치
```

## 미등록이어도 역질문을 끝까지 하는 이유

없는 약관이면 바로 「없습니다」로 끝내는 편이 빠르다. 그런데도 상품명과
가입 시점을 먼저 묻는 이유는, **등록 요청이 「상품」이 아니라 「상품 + 판」
단위여야 하기 때문**이다.

상품명만 알면 어느 판을 등록해야 하는지 정해지지 않는다.
개정 이력이 있는 상품은 판이 여럿이고, 그중 FA에게 필요한 것은 그 계약의 판 하나다.
가입 시점을 받아야 등록 대상이 하나로 좁혀진다.

역질문이 두 가지 일을 겸하는 셈이다.

1. 등록된 약관이면 → 정확한 판으로 검색
2. 미등록 약관이면 → 정확한 등록 대상 수집

FA 입장에서 두 경우의 대화가 같으므로, 이 상품이 등록됐는지 몰라도 된다.

## 세 갈래 처리

| 상황 | 처리 |
| --- | --- |
| 벤더 인덱스에 약관 있음 | 판 특정 후 검색 · 답변 |
| 마스터에는 있으나 약관 미등록 | 시점 확인 → 없다고 안내 + 요청 기록 (상품 ID 포함) |
| 마스터에도 없는 이름 | 시점 확인 → 없다고 안내 + 요청 기록 (이름만) |

세 번째를 「모르는 상품입니다」로 끝내지 않는 것이 중요하다.
그렇게 하면 우리가 모르는 상품일수록 요청이 쌓이지 않아,
정작 필요한 약관이 등록 목록에 영영 오르지 않는다.
오타로 들어온 이름은 요청 건수가 낮아 우선순위에서 자연히 밀린다.

## 우선순위 집계

`RequestLog.priorities()`가 요청을 빈도순으로 돌려준다.

- 집계 단위는 **보험사 + 상품 + 가입 연도**다.
  같은 상품이라도 가입 연도가 다르면 필요한 판이 다를 수 있다.
- 건수가 같으면 먼저 요청된 것을 앞에 둔다. 오래 막혀 있던 것을 먼저 푼다.
- 대표 요청에 원 질문이 남으므로, 어떤 맥락에서 필요했는지 함께 볼 수 있다.

## 초기 100건을 무엇으로 채울까

초기 목록은 요청 데이터가 없는 상태에서 정해야 한다. 다음 순으로 보는 것이 안전하다.

1. **보유 계약이 많은 상품** — 보상 질문은 이미 가입한 계약에서 나온다
2. **보상 문의가 잦은 상품군** — 실손 · 암 · 운전자 등
3. **개정 이력이 많은 상품** — 판을 헷갈리기 쉬워 FA가 확인을 더 필요로 한다

1번은 계약 데이터(Cloud DATA)를 보면 바로 나오지만 이번 범위 밖이므로,
영업·보상 쪽에서 목록을 받아 정하는 편이 빠르다.

## 운영에서 볼 지표

- **미등록 비율** — 보상 질문 중 「약관 없음」으로 끝난 비율.
  이 값이 등록 확대의 근거가 된다.
- **역질문 이탈** — 되물었는데 FA가 답하지 않고 나간 비율.
  높으면 되묻기가 과하거나 선택지가 잘못됐다는 신호다.
- **요청 상위 목록** — 다음 배치에 넣을 약관.
